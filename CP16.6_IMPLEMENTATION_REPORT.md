## Summary

CP16.6 bridges the three representations of a portal's enabled state so they no longer silently diverge:

1. **`job_sources.enabled / status`** in SQLite — *administrative intent* (SQLAlchemy/API)
2. **`.agents/skills/<adapter>/SKILL.md` frontmatter `enabled`** — *runtime gate* consumed by `/job-scraper` (CP15.5)
3. **`portal_health.json` `disabled` fields** — *CP15.5 event bookkeeping*

The two runtime files retain their authoritative role; the DB intent is propagated to them (never the reverse, except via the health API's read-only divergence visibility). Making the SKILL.md gate the single write-through source keeps the execution gate in place.

## Exact Behavior

### 1. Admin → runtime write-through (PATCH `/api/admin/sources/{id}`)
- When `enabled` is sent (either value), the DB row's `enabled` is updated **and** its `status` is driven to `enabled`/`disabled`.
- **Enable** requires a valid, known `adapter_name` (`is_known_skill_name`, e.g. `indeed-search`) **and** an installed `.agents/skills/<adapter>/SKILL.md`. Otherwise → **400** with `"no files were modified."` and no runtime/DB file change (the DB intent is rejected outright rather than creating a half-state).
- **Disable** is tolerant: if the SKILL.md is missing it is skipped (the runtime already effectively gates it off) but the health store is still updated.
- Write-through order: DB commit/refresh → `set_skill_enabled` → `update_health_store`. Every file write is atomic `tmp + rename`, then **read-back verified** (mismatch raises).
- **Failure semantics:** a later write-through failure triggers compensating rollback — the SKILL.md is reverted via `set_skill_enabled(target, prev_enabled)`, all captured prior DB fields and `status` are restored, and a **500** with `"DB and runtime state rolled back to their prior values"` is returned. A known half-state is never left silently.
- **Idempotent:** an `enabled` equal to the current SKILL.md value skips the write (no file churn); `update_health_store` skips a write when the loaded portal entry already has the target `disabled` value.

### 2. CP15.5 → DB best-effort write-through (`job_scraper/portal_health.js`)
- **Auto-disable** (runCheck 403 threshold): `syncJobSourceEnabled(portal, false, { guardEnabledOnly: true })` — matches `adapter_name = ? AND enabled = 1 AND status = 'enabled'`, so **only** rows whose intent is currently `enabled` are disabled. `APPROVED` / `READY_FOR_REVIEW` / `DISCOVERED` rows are never auto-disabled.
- **Manual toggle**: `manual disable` → `enabled=0/status='disabled'` (unguarded); `manual enable` → `enabled=1/status='enabled'` (restores a previously auto-disabled row).
- **Best-effort:** `node:sqlite` unavailable, missing DB file, missing `job_sources` table, invalid row, or sync error all degrade to a logged no-op that never fails CP15.5. Missing DB is detected via `fs.existsSync` **before** opening (opening a missing file would create it).
- **Opt-in:** DB writes fire only when `--db` / `PORTAL_DB_FILE` / library `db` option is provided. Without one, CP15.5 runs exactly as before and existing tests never touch `backend/careerpilot.db`.
- **Scheduled runs (CP15.3 `portal-health`):** the schedule prompt now runs `node job_scraper/portal_health.js check --db backend/careerpilot.db`. The `--db` flag flows `parseArgs → runCheck(options) → syncJobSourceEnabled(portal, false, { ...options, guardEnabledOnly: true })`, so the CP16.6 auto-disable DB mirror is armed in daily scheduled runs, not only manual/CLI use. The trailing prompt guard ("Do not run health checks if invoked outside an active Claude Code session") is preserved from the original schedule.
- `--dry-run` writes nothing: no DB, no SKILL.md, no health state (verified by test).

### 3. Health API divergence visibility (additive only)
- `PortalHealthStatus` exposes `skill_enabled` (already present) and now `job_source_enabled: Optional[bool]`.
- `_build_portal_status` reads the DB row by `adapter_name` (with legacy `name` fallback via the portal registry) through `read_job_source_enabled` — a defensive read-only sqlite3 open (`PRAGMA query_only = ON`, 2s timeout) returning `None` on any DB/table/row absence.
- No existing field renamed, removed, or replaced. Existing `test_portal_health.py` (20 tests) passes unchanged with no DB available.

### 4. Tests
- **Backend (`test_enabled_bridge.py`, 14):** admin enable → DB+SKILL+health; admin disable → DB+SKILL+`admin disable` reason; enable with missing/unknown adapter → 400 + no SKILL modification; enable with missing SKILL.md → 400; repeated toggle → byte-identical files (no churn); write-through failure → compensating rollback restores DB + SKILL.md + no health file; health API exposes both states and detects simulated divergence; reader adapter/name/priority/no-row/missing-file/missing-table.
- **JS (`portal_health.test.js` §22, 8):** guard-only-touches-enabled rows; manual disable→enable restores; no matching row succeeds; missing DB no-op; runCheck auto-disable syncs matching enabled row + leaves approved untouched; runCheck succeeds with missing DB; manualToggle mirrors DB; CLI `check --dry-run` → no DB/SKILL/health writes.

## Rollback / Failure Semantics

- **Backend PATCH:** DB committed first; SKILL.md and health written after. On file-write failure → compensating rollback restores the SKILL.md and the prior DB fields/status, then 500. Read-back verification catches silent mismatch. The 400 enable path never touches files or DB.
- **JS nearest-equivalent on repeated failure:** `syncJobSourceEnabled` is a single best-effort statement per toggle; because CP15.5's own file write precedes it and CP15.5's existing semantics are untouched, a sync failure leaves the SKILL.md (the runtime gate) as the authoritative state and only logs — it does not corrupt the DB or fail the run.

## Remaining Limitations

- **DB write-through is armed per-invocation and point-in-time, not a continuous sync.** Scheduled runs arm it via the `portal-health` schedule prompt's `--db`; manual/CLI users pass `--db` or `PORTAL_DB_FILE` (default `backend/careerpilot.db`). It fires only on the toggle events CP15.5 already handles, so a run with no portal exceeding the 50% threshold makes no DB changes. A future run's DB rows therefore reflect the last write-through, matching CP15.5's existing one-way SKILL.md→health flow. Plain calls without DB opt-in (and all tests) never touch `backend/careerpilot.db`.
- **`orchestrator.js` bypass** of the SKILL.md gate is a pre-existing, documented caveat and is explicitly **not** a CP16.6 target.
- Filesystem + SQLite remain two stores; CP16.6 uses compensating rollback + read-back verification rather than claiming atomicity.
- The JS side matches `job_sources` by `adapter_name` (the admin bridge sets this on install/adapter rows); legacy rows without `adapter_name` are not auto-synced by JS (the backend reader still resolves them by `name`).
