## 3. Public Architecture Changes

Structural separation, not runtime toggling. Implemented rules:

- **No private-endpoint calls on public data flows.** Public pages import only public hooks (`usePublicJob`, `usePublicApplications`, `usePublicRetentionStats`); private hooks (`useJobs`, `useApplications`, `usePipelineStatus`, `useRetentionStats`, saved-jobs/pipeline hooks) are never referenced by public pages.
- **No auth-based data selection.** Public pages do not check for a JWT, do not branch on auth state, and never fall back between public/private datasets. No `demo=true` runtime switch exists anywhere.
- **No public access to private endpoints / real database / real applications / real profile / real documents.** Public pages consume only `GET /api/public/jobs/{stable_id}`, `GET /api/public/jobs`, `GET /api/public/applications`, and `GET /api/public/retention`, all served from the fictional `DemoDataStore`. No download/generate of real documents.
- **No anonymous mutations.** Public pages contain no mutation controls (see §9).
- **Public vs private flows stay structurally separate:** private pages (`JobDetail`, `FitAnalysis`, `Pipeline`, `RetentionStats`, ranked/applications/dashboard private variants) are untouched and continue to use their private hooks and protected routes.
- **Safe external links:** the public job detail renders the original posting via `safeExternalUrl()` (http/https only).
- **Schema discipline:** one canonical public application schema (`PublicApplicationRecord`); no broad `any` in produced public consumers.

## 8. Public Applications Schema Fix (F-2)

- **Canonical schema:** added `PublicApplicationRecord` to `frontend/src/api/types.ts` — `stable_id, date, company, sector, role, role_type, channel, status, contact_person, fit_rating (0-100), notes, cv_file, cover_letter_file, source`. Matched exactly against the live public payload keys (all 16 demo records conform).
- **Stable-ID join:** `PublicApplications.tsx` and `PublicDashboard.tsx` now resolve the linked demo job via `app.stable_id` (previously the P4.2 schema drift assumed `job_stable_id`). Verified by test: the resolved titles (`IT Support Specialist`, `Systems Administrator`) prove the join is correct.
- **Dates:** application table now shows the `date` field as "Application Date" (`yyyy-MM-dd`), matching the canonical schema; obsolete `updated_at`/`created_at` references removed.
- **Duplicate keys:** React list keys uses `app.stable_id` (unique) in both the applications table and the dashboard recent-applications list. A duplicate-key regression test spies on `console.error` and asserts no duplicate-key warnings.
