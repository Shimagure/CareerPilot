## Key Architectural Finding

**CronCreate is a Claude Code session tool, not a Node.js API.** There is no npm package, HTTP endpoint, or system command that exposes it to `scheduler.js`. The CP15 architecture assessment's original description of `scheduler.js` as a "CronCreate wrapper" is not implementable as stated.

**Resolution:** `scheduler.js` is the persistent schedule registry/CLI (survives session restarts via `job_scraper/schedules.json`). Claude Code performs the actual CronCreate installation:
1. At session start, Claude runs `node job_scraper/scheduler.js prompts`
2. Claude creates a CronCreate job per enabled schedule using the returned `name`, `cron`, `recurring`, and `prompt`
3. When a CronCreate job fires, Claude receives the prompt and executes the existing workflow

**CronCreate lifetime limitations:**
- Jobs are **session-scoped** — they exist only while a Claude session is active
- Recurring jobs **auto-expire after 7 days**
- The registry (`schedules.json`) is durable; the installed CronCreate jobs are not

## Schedule Definitions

| Name | Cron | Recurring | Enabled | Description |
|---|---|---|---|---|
| `incremental` | `57 8 * * *` | true | yes | Daily incremental job search |
| `weekly-audit` | `13 9 * * 6` | true | no | Optional Saturday full audit |
| `portal-health` | `47 11 * * *` | true | yes | Daily portal health check |

**No stale-reverification schedule exists.** The original architecture proposed a separate stale re-verification schedule (every 2 days). This was intentionally removed: the CP15.1 orchestrator's existing priority queue already processes stale jobs during any incremental run, and the `--resume` flag handles resumption. Adding a separate stale-only schedule would be redundant and would duplicate state-machine semantics.

## CLI Behavior

```
node job_scraper/scheduler.js list              # Show all schedules + status
node job_scraper/scheduler.js get <name>        # Full definition for one schedule
node job_scraper/scheduler.js enable <name>     # Set desired state = enabled
node job_scraper/scheduler.js disable <name>    # Set desired state = disabled
node job_scraper/scheduler.js prompts           # Enabled schedules as CronCreate-ready JSON
node job_scraper/scheduler.js --help            # Usage
```

### Verified behavior
- `list` shows name, cron, enabled state, description, Active/Disabled counts, and the session-scoped CronCreate limitation
- `get <name>` prints the complete schedule definition as JSON
- `enable`/`disable` mutate **only** the `enabled` flag in `schedules.json` (desired state); they do not touch any actual CronCreate job
- `prompts` outputs **only enabled schedules** with exactly `name`, `cron`, `recurring`, `prompt` fields
- Unknown schedule names exit non-zero with a useful error naming available schedules
- Unknown commands exit non-zero
- Missing name argument (`get`, `enable`, `disable`) exits non-zero
- Malformed JSON or missing `schedules` field in `schedules.json` exits non-zero with a safe error, and does not write anything

### Enable/disable semantics
The `enabled` flag records **desired state** in the registry. Because CronCreate jobs are session-scoped and auto-expire after 7 days, an enabled schedule in the registry is **not** guaranteed to be installed in the active Claude session. Reconciliation is Claude Code's responsibility:
- `disable <name>` → registry updated + Claude deletes any matching live CronCreate job
- `enable <name>` → registry updated + Claude creates the CronCreate job (on next `prompts` pull)
- The `list` output and this report document that this reconciliation is manual/Claude-driven

## Prompt Contracts

Each prompt is explicit that Claude should **execute the existing workflow, not invent a new pipeline**:

| Schedule | Prompt contract |
|---|---|
| `incremental` | Invoke `/scrape` in INCREMENTAL mode; after successful `ranking_report`, read `run_id` from `checkpoints.json`; run `python job_scraper/sync_to_db.py --run-id <run_id>`; report sync summary |
| `weekly-audit` | Invoke `/scrape` in FULL_AUDIT mode (`/full-job-audit`); after successful `ranking_report`, read `run_id` from `checkpoints.json`; run CP15.2 sync; report summary |
| `portal-health` | Run `node job_scraper/portal_health.js check --db backend/careerpilot.db` (CP15.5 CLI, CP16.6 DB mirror armed); report portal health status |

Prompts never claim that `scheduler.js` itself can call CronCreate. Health prompts never reference sync or pipeline stages (CP15.5 owns detection/disable logic).

## Issues & Deviations

1. **`$LASTEXITCODE` display quirk during manual verification** (PowerShell): initial manual exit-code checks printed an empty value due to shell chaining; re-verified with explicit `$?` in Bash — exit codes are correct (1 for errors). Non-issue.

2. **Testability required one scheduler.js edit**: `SCHEDULES_FILE` now honors `process.env.SCHEDULER_FILE` (defaults to `path.join(__dirname, 'schedules.json')`). This preserves the default behavior exactly while allowing tests to isolate file writes. No behavior change in normal operation.

3. **No data-file rewrite risks**: `enable`/`disable` rewrite `schedules.json` with `JSON.stringify(config, null, 2)` preserving key order and formatting. No unrelated data is touched. Atomic write (temp + rename) is not used for this small file, which matches the orchestrator's `saveJSON` pattern.
