## 1. Operational Error Leakage Prevention

Client-facing responses no longer echo internal exception text, filesystem paths, or implementation details. Full diagnostics remain server-side via `logging.exception()`.

### 1.1 Search pipeline run failures
`backend/app/services/search_manager.py:244`

- **Before:** `run.error = f"Execution error: {type(e).__name__}: {e}"` — an exception such as `sqlite3.OperationalError ... 'C:/private/app/secrets/master.db'` was sent verbatim to the client's `SearchRunResponse.error`.
- **After:** `run.error = "Search pipeline execution failed."` — a fixed, safe client-facing message.
- The full exception is logged server-side through `logger.exception(...)` immediately before, preserving diagnosability.

### 1.2 Admin source analysis (`feasibility`)
`backend/app/routers/admin_sources.py:526`

- Any unexpected exception during analysis is mapped to `feasibility: "error"`. Exception text is never written into the analysis response.
- Timeout and redirect-loop cases map to safe, distinct values (`timeout`, `redirect_loop`).

### 1.3 Enabled-state bridge write-through failure
`backend/app/routers/admin_sources.py:275-278`

- **Before:** the exception message (e.g. `[Errno 13] Permission denied: 'C:/private/.../SKILL.md'`) was exposed in the HTTP 500 `detail`.
- **After:** a fixed, actionable message: *"Enabled-state bridge write-through failed; DB and runtime state rolled back to their prior values."* The original exception remains server-side via `logging.exception()`-style handler context.
- Compensating rollback behavior (restore prior DB row + runtime file on write-through failure) is preserved.

## 2. Admin SSRF / DNS-Rebinding Protection

New module `backend/app/ssrf.py` + hardening of `analyze_url` in `backend/app/routers/admin_sources.py`.

**Original finding (read-only P3.3-only review):** validation checked resolved IPs once, then httpx connected using its own independent DNS lookup via `anyio.connect_tcp` — the classic DNS-rebinding / DNS TOCTOU: a hostname validated against a public IP could be re-resolved to a private address at connect time and reach an internal destination. **Remediated here** by deleting the gap between validation and connect: the fetch path now rewrites the connect target to the validated IP literal, so no second lookup can ever reach the destination. (httpx 0.28 removed the resolver API, verified against the installed packages, so the pin is enforced in the transport, not a resolver.)

### 2.1 Validation model (`app/ssrf.py`)

`validate_outbound_url(url, *, allow_redirect=False)` performs, in order:

1. **Scheme allowlist** — only `http` / `https`.
2. **Hostname blocklist** — `localhost`, `localhost.localdomain`, and cloud metadata endpoints are rejected before any resolution (no network access).
3. **IP-literal validation** — if the host is an IPv4/IPv6 literal, it is validated directly with no DNS call.
4. **DNS resolution + resolved-IP safety** — every address returned by `socket.getaddrinfo` is checked. If **any** resolves to a non-public address, the URL is rejected (an attacker-controlled hostname returning mixed public + private addresses is still blocked).

Non-public destinations blocked (each with a specific, safe message):
`loopback`, `private`, `link-local`, `reserved`, `unspecified`, `CGNAT (100.64.0.0/10 -- not covered by is_private on all Python versions)`, plus the binding of `169.254.169.254` / `metadata.*` as **metadata endpoints**.

- `BlockedDestinationError` (a `ValueError` subclass) carries a short, specific, client-safe message ("Access to private addresses is blocked", etc.). Callers can map it to a 400 while differentiating blocked vs. malformed.
- **In `allow_redirect=True` mode** any failure returns `None`, so redirect-follower callers treat a bad redirect as "do not follow" without raising.

### 2.2 Validation result carries the exact validated IPs

`validate_outbound_url` returns a `UrlValidation` dataclass — `scheme`, `hostname`, and `resolved_ips` (the exact tuple of addresses that passed the public-only safety check). This tuple is the pin set the fetch layer consumes; the connection path performs **no independent DNS lookup**.

### 2.3 IP-pinning transport (`app/ssrf.py` — `PinnedTransport`)

httpx **0.28** / httpcore **1.x** removed the resolver abstraction (verified against the actually-installed packages: `httpx.AsyncResolver` does not exist and `resolver=` is not a valid httpx knob). Connections are opened by handing the request host directly to `anyio.connect_tcp`, which performs an uncontrolled DNS lookup — the DNS-rebinding TOCTOU flagged by the read-only review. `PinnedTransport` (an `httpx.AsyncHTTPTransport` subclass) closes that gap:

- **`handle_async_request`** rewrites the request URL's host to a validated IP selected from `resolved_ips` (deterministic IPv4-first precedence), so the actual TCP connect — httpcore's `connect_tcp(host=self._origin.host)` — targets the validated IP **literal**. No hostname resolution occurs for a pinned host, so a second lookup cannot re-route the connection.
- **Host header preserved:** httpx passes our explicit `Host` header through httpcore verbatim (`include_request_headers`); the **original hostname** (bracketed for IPv6, with non-default port when present) is injected — never the pinned IP.
- **TLS SNI / certificate validation preserved:** the `sni_hostname` httpcore extension is set to the original hostname; httpcore's `_connect` uses `server_hostname = sni_hostname or origin.host`, so SNI and cert hostname matching keep the original name.
- **Fail-closed:** a request whose hostname is not in the pinned map raises `httpx.ConnectError` (labeled *unvalidated host*) — it never falls back to an uncontrolled resolver.
- Scheme allowlist, hostname blocklist, and private/loopback/link-local/reserved/unspecified/CGNAT/metadata blocking are unchanged. `network_backend` is injectable post-construction only as a test seam (httpcore's documented `AsyncNetworkBackend`); production always connects to the validated IP.

### 2.4 Main analysis + robots.txt both pinned (`admin_sources.py`)

- **Main request:** `analyze_url` pins `{validation.hostname.lower(): validation.resolved_ips}` and issues the GET through `httpx.AsyncClient(transport=PinnedTransport(pinned_hosts, trust_env=False), trust_env=False)`. `trust_env=False` also prevents any proxy from re-routing the request.
- **Robots.txt:** built from the sanitized base (`scheme://<host>[:port]/robots.txt`, no userinfo), validated with `allow_redirect=True`, and fetched through its own `PinnedTransport` pinned to the robots host's validated IPs.

### 2.5 Redirect revalidation + re-pinning

Redirects are followed manually (max 3), never automatically:
- Before each hop, `validate_outbound_url(next_url)` re-validates the destination (scheme + DNS + resolved-IP safety).
- `BlockedDestinationError` → `feasibility: "error: <safe message>"`, response returned, redirect **not followed**.
- Other `ValueError` → `feasibility: "redirect_loop"`, not followed.
- A fresh validated result re-pins the map (`pinned_hosts = {next_validation.hostname.lower(): next_validation.resolved_ips}`) and the next hop opens a **new** transport for that destination — no stale pin survives a redirect.

### 2.6 Remaining limitations

- Pinning trusts that a validated public IP remains that same host for the request lifetime; it does not protect against a validated server that fronts both public and internal content on one IP (a reverse-proxy class of issue, not address-rebinding).
- `socket.getaddrinfo` is snapshotted at validation time and enforced by construction thereafter; an operator with control of the validating environment could influence what gets pinned, but the pin set is immutable for the request.
- Redirect loops, non-HTML content, timeouts, and the 3-hop cap behave exactly as before.

The common SSRF vectors — scheme smuggling, private/loopback/link-local/metadata literals, mixed-resolution hostnames, redirect hops to non-public destinations, and rebinding between validation and connect — are all blocked or fail closed.

## 3. Security Audit Logging

New module `backend/app/audit.py`; wired into auth and admin actions.

### 3.1 Format and storage
- Structured **JSON-line** records to `<project_root>/logs/audit.log`.
- `RotatingFileHandler` — bounded at **5 MB** with **3 backups** (max ~20 MB on disk).
- `logging.Formatter("%(message)s")` emits one JSON object per line for easy `jq`/parser consumption.
- UTC ISO-8601 timestamps.

### 3.2 Auth events (`backend/app/routers/auth.py`)
| Event | Trigger | Fields |
|---|---|---|
| `login_success` | valid creds, active account | ts, cat=auth, event, uid, email(masked), ip |
| `login_failure` | bad creds / unknown email | ts, cat=auth, event, email(masked), ip, detail |
| `login_failure` (account inactive) | valid creds, inactive account | ts, cat=auth, event, uid, email(masked), ip, detail |
| `register_success` | account created | ts, cat=auth, event, uid, email(masked), ip |
| `register_failure` | duplicate email | ts, cat=auth, event, email(masked), ip, detail |

### 3.3 Admin events (`backend/app/routers/admin_sources.py`)
| Event | Trigger | Fields |
|---|---|---|
| `source_update` | PATCH `/{id}` | ts, cat=admin, action, uid, target_type=source, target_id, detail(updated fields), ip |
| `source_delete` | DELETE `/{id}` | ts, cat=admin, action, uid, target_type=source, target_id, ip |
| `source_analyze` | POST `/analyze` or `/{id}/analyze` | ts, cat=admin, action, uid, target_type=source, target_id(safe host only), detail(scheme://host[:port] + bounded path), ip |

### 3.4 Data-minimization guarantees (enforced by construction + tests)
- **Emails are masked** (`_mask_email`): first two local-part chars + `***` + domain (e.g. `vi***@example.com`). The raw address never appears.
- **Passwords, JWTs, access tokens, and secrets are never logged** — the login/register bodies and tokens are not passed to the logger; the full-format test asserts the log text contains none of them.
- No exception text, filesystem paths, or implementation details are written to the audit log.

### 3.5 Admin `source_analyze` URL sanitization

**Original finding (read-only review):** the `source_analyze` audit event derived `target_id`/`detail` from the raw URL, which could leak userinfo (`https://user:pass@host/...`), query strings, fragments, or embedded tokens/API keys into the audit log. **Remediated** by logging only normalized destination data via `safe_destination_summary()` (`app/ssrf.py`):

- `scheme`; `host` taken from `urlparse(...).hostname`, which **strips any userinfo** — credentials structurally absent;
- optional non-default `port`;
- `path` bounded to 100 chars;
- `target_id` is the safe host only (fallback: scheme, then `"unknown"`) — it **never falls back to the raw URL**;
- `detail` is `Analysis of <scheme>://<host[:port]><path>`.

Query strings, fragments, access tokens/API keys, and arbitrary URL params can never appear because they are never part of the constructed fields. Tests assert the sensitive values (query values, `user:pass@`, fragment) do not appear anywhere in the audit log text.
