## EXECUTIVE SUMMARY

The live SQLite database (`backend/careerpilot.db`) reports **alembic_version = 2b3c4d5e6f78** (HEAD), yet the **`job_sources` table is completely absent** from `sqlite_master`. All 26 existing users have `role='user'` (lowercase values) while the SQLAlchemy `Enum(UserRole)` expects uppercase names (`USER`, `ADMIN`). The `JobSource` model has identical enum mismatches for `source_type` and `status` columns.

## A. WHY ALEMBIC_VERSION REPORTS HEAD WHILE JOB_SOURCES TABLE IS MISSING

### Evidence
| Check | Result |
|-------|--------|
| `alembic_version` table | `2b3c4d5e6f78` (HEAD) |
| `sqlite_master` tables | 9 tables: `alembic_version`, `users`, `applications`, `resumes`, `search_preferences`, `search_runs`, `user_jobs`, `candidate_profiles`, `jobs` |
| `job_sources` table | **ABSENT** (no entry in `sqlite_master`) |
| Migration `2b3c4d5e6f78` | Contains `op.create_table('job_sources', ...)` |

### Root Cause
**The migration was recorded as applied (version stamped) but the `CREATE TABLE job_sources` DDL never executed or was rolled back silently.** This is possible in SQLite when:
1. **Alembic runs in a transaction** that commits the version stamp but the DDL fails/rolls back
2. **Dual schema-creation paths** — `Base.metadata.create_all()` (used in tests and possibly early runs) creates tables without stamping alembic_version, then a later `alembic upgrade head` stamps the version without re-running DDL for tables that "already exist" (but `job_sources` didn't exist at that time)
3. **Conditional migration logic** — The migration may have had a check that skipped `job_sources` creation

### Migration 2b3c4d5e6f78 Analysis
The migration `2b3c4d5e6f78_add_user_name_role_and_job_sources.py` contains:
- `op.add_column('users', sa.Column('name', ...))`
- `op.add_column('users', sa.Column('role', ...))`
- `op.create_table('job_sources', ...)`

The `users` table **has** the `name` and `role` columns (verified via `PRAGMA table_info(users)`), proving the `ADD COLUMN` operations ran. The `CREATE TABLE job_sources` did not.

## B. WHETHER MIGRATION 2B3C4D5E6F78 CREATE_TABLE COULD CONDITIONALLY SKIP/FAIL ON SQLITE

### Code Inspection
```python
# In migration 2b3c4d5e6f78:
op.create_table(
    'job_sources',
    sa.Column('id', ...),
    sa.Column('name', ...),
    sa.Column('source_type', sa.Enum('direct_employer', 'job_board', 'government_portal', 'custom_feed', name='job_source_type')),
    sa.Column('status', sa.Enum('discovered', 'analyzing', 'ready_for_review', 'approved', 'enabled', 'disabled', name='job_source_status')),
    ...
)
```

### SQLite Enum Behavior
- SQLite **does not have native ENUM type** — SQLAlchemy emulates it via `CHECK` constraints or stores as `VARCHAR`
- `sa.Enum(..., name='...')` with `create_constraint=True` (default) creates a `CHECK` constraint
- **No known SQLite-specific failure mode** for `CREATE TABLE` with enum columns that would silently skip table creation

### Conclusion
The `CREATE TABLE` **should have executed**. The fact that it didn't — while `ADD COLUMN` for `users` did — strongly suggests:
1. The migration ran **partially** (some operations committed, others didn't)
2. OR `Base.metadata.create_all()` ran **after** the migration stamped the version, but `job_sources` wasn't in `Base.metadata` at that time (unlikely — model exists)
3. OR the database was **copied/replaced** after migration stamping but before `job_sources` creation

## C. HOW LIVE DB REACHED THIS STATE

### Timeline Reconstruction
| Date | Event |
|------|-------|
| 2026-09-07/08 | 26 users registered (created_at timestamps) |
| 2026-09-11 | Migration `2b3c4d5e6f78` dated (per filename) |
| 2026-09-12 | Current investigation |

### Possible Scenarios (ranked by likelihood)
1. **Failed partial migration** — Migration ran in transaction; `ADD COLUMN` succeeded, `CREATE TABLE` failed (constraint? disk full? lock?), transaction partially committed version stamp
2. **create_all vs Alembic race** — Early app startup ran `create_all()` (creating users table without `name`/`role`), then migration added columns and stamped version, but `job_sources` model wasn't imported/registered in `Base.metadata` at `create_all` time
3. **Stale DB copy** — A backup/restore or container volume mount brought an older DB file that had the alembic_version stamp but not the table
4. **Multiple migration paths** — Alembic upgraded on one DB file, app connected to different file

### Key Evidence Against "create_all created everything"
- Tests use `create_all` on **temp databases** — they pass because temp DBs get fresh schema with enums as NAMES
- Live DB has `role` column with **default `'user'` (lowercase)** — this came from the migration's `server_default="user"`, not from `create_all` (which would use `UserRole.USER` → `'USER'`)

## F. RECONCILE ENUM ISSUE: STORAGE CONVENTION VS MODEL EXPECTATIONS

### The Core Mismatch
| Model | Python Enum | DB Storage (Migration) | DB Storage (create_all) | Live DB Values |
|-------|-------------|------------------------|-------------------------|----------------|
| `User.role` | `UserRole.USER` / `ADMIN` | `'user'` / `'admin'` (VALUES) | `'USER'` / `'ADMIN'` (NAMES) | `'user'` (all 26 users) |
| `JobSource.source_type` | `JobSourceType.JOB_BOARD` etc. | `'job_board'` etc. (VALUES) | `'JOB_BOARD'` etc. (NAMES) | N/A (table missing) |
| `JobSource.status` | `JobSourceStatus.DISCOVERED` etc. | `'discovered'` etc. (VALUES) | `'DISCOVERED'` etc. (NAMES) | N/A (table missing) |

### Why Tests Pass But Login Fails
- **Tests**: Use `create_all` on temp DBs → enums stored as **NAMES** (`'USER'`, `'ADMIN'`) → SQLAlchemy `Enum(UserRole)` reads NAMES → **works**
- **Live DB**: Migration wrote **VALUES** (`'user'`, `'admin'`) → SQLAlchemy `Enum(UserRole)` expects NAMES → **`LookupError` on load** → login 500s before password check

### SQLAlchemy Enum Behavior
```python
# In database_models.py:
role: Mapped[UserRole] = mapped_column(Enum(UserRole), default=UserRole.USER, nullable=False)
```
- **Default `Enum` behavior**: `values_callable=lambda obj: [e.value for e in obj]` — stores **VALUES**
- **But**: When reading, SQLAlchemy looks up by **NAME** (enum member name)
- **Result**: DB has `'user'`, enum has `USER` (name) → **mismatch**

### The Fix: Pick ONE Convention
| Option | Change Required | Pros | Cons |
|--------|----------------|------|------|
| **A. Store VALUES (lowercase)** | Change `Enum(UserRole)` → `Enum(UserRole, values_callable=lambda x: [e.value for e in x])` + ensure `native_enum=False` | Matches live DB; migration used this | Must verify all enum columns |
| **B. Store NAMES (uppercase)** | Update live DB: `UPDATE users SET role='USER' WHERE role='user'`; future migrations use names | Matches `create_all`/tests | Migration already wrote values; requires data migration |

### Recommendation: **Option A — Store VALUES (lowercase)**
- **Reason**: Live DB already has 26 users with `'user'`; migration DDL used values; changing to names requires data migration on every enum column
- **Implementation**: Add `native_enum=False, values_callable=lambda obj: [e.value for e in obj]` to ALL `Enum(...)` columns in `database_models.py`
- **Affected columns**: `User.status`, `User.role`, `Resume.status`, `SearchRun.status`, `UserJob.status`, `Application.status`, `JobSource.source_type`, `JobSource.status`
