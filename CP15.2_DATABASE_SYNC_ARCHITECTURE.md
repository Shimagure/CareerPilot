# CP15.2 Database Sync Architecture

**Date:** 2026-09-10  
**Status:** ARCHITECTURE ANALYSIS ONLY — no implementation performed  
**Scope:** Define the safe architecture for synchronizing the incremental job-scraper state with SQLite/PostgreSQL without changing pipeline behavior or user application data.

---

## 1. Executive Summary

The current backend does **not** contain a global `jobs` table. The pipeline's global job dataset remains in JSON files under `job_scraper/`, and the backend reads those files through `backend/app/store.py`.

The SQL database currently stores:

- users and authentication data;
- candidate profiles, resumes, and search preferences;
- search-run lifecycle records; and
- user-owned references to jobs through `user_jobs.job_stable_id` and `applications.job_stable_id`.

Therefore, CP15.2 cannot safely be implemented as an upsert into an existing table. It requires a new global `jobs` table plus an explicit synchronization boundary.

### Recommended architecture

1. **Pipeline JSON remains the write-authoritative source for scraper state.**
2. **A new SQL `jobs` table becomes a read-optimized mirror for the backend/API.**
3. **Sync is one-way: `seen_jobs.json` plus ranking/canonical data → SQL `jobs`.**
4. **User-owned rows (`user_jobs`, `applications`) remain authoritative for user state and are never overwritten by the scraper sync.**
5. **The sync must be idempotent, transactional, dialect-neutral, dry-run capable, and protected by a single-writer lock.**
6. **Sync should consume the stable ID inside each job record, not the top-level portal/job key in `seen_jobs.json`.**

This design preserves the existing scraper state machine while allowing the backend to stop depending on filesystem reads in a later checkpoint.

## 2. Current Architecture Findings

### 2.1 Pipeline data sources

The current pipeline persists job state in:

| File | Current role | Sync relevance |
|---|---|---|
| `job_scraper/seen_jobs.json` | Persistent state database containing processing state, fingerprints, verification data, scores, and ranks | **Primary sync input** |
| `job_scraper/canonical_jobs.json` | Canonicalized job records used by filtering and backend reads | Supplemental field source; use to fill fields absent from `seen_jobs` |
| `job_scraper/ranked_jobs.json` | Expected ranked artifact referenced by backend config and some scripts | Optional ranking input when produced |
| `job_scraper/ranked_jobs_YYYYMMDD.json` | Dated ranking/report artifact written by the legacy ranking script | Audit artifact, not a stable integration contract |
| `job_scraper/checkpoints.json` | Pipeline progress and recovery state | Sync gate and audit metadata; not a job source |
| `job_search_tracker.csv` | CLI application tracker | Must not be rewritten by SQL sync |

`seen_jobs.json` has the shape `{ "seen": { <portal_or_source_key>: <job_record> }, ... }`. The source key is not the canonical identity. Each record contains a 64-character SHA-256 `stable_id`; that value is the only supported SQL identity.

### 2.2 Backend read path

`backend/app/store.py` currently:

- loads `canonical_jobs.json`, `seen_jobs.json`, and `ranked_jobs.json` directly;
- merges canonical fields with state/scoring fields from `seen_jobs`;
- resolves application protection by reading the CSV tracker and matching company/title to stable IDs;
- exposes `JobRecord` and `JobSummary` through the jobs and ranked routers.

The current `RANKED_JOBS_FILE` setting points to `job_scraper/ranked_jobs.json`, but the CP15.1 orchestrator treats aggregated `seen_jobs.json` as authoritative for the final ranking state because the active ranking script writes rank fields back into `seen_jobs.json`. This discrepancy must be resolved before implementation rather than silently choosing a dated file.

### 2.3 Existing SQL model boundary

`backend/app/models/database_models.py` defines:

- `UserJob`: `(user_id, job_stable_id)` unique association with saved/viewed/interested/dismissed/analyzed status;
- `Application`: user-owned application record keyed by `job_stable_id`, with company and role snapshots plus application timeline/document fields;
- no `Job` model and no foreign key from either user-owned table to a global job table.

The Alembic initial migration confirms that the existing schema contains no `jobs` table. The absence of a global table is intentional in the current implementation: the JSON pipeline is the global job source and SQL stores only user-specific state.

## 3. Required Sync Boundary

### 3.1 Direction of synchronization

**Recommended direction:**

```text
portal discovery and pipeline stages
        ↓
canonical_jobs.json / seen_jobs.json
        ↓
CP15.2 sync transaction
        ↓
SQL jobs mirror
        ↓
backend API and future frontend reads
```

There must be no reverse synchronization of job fields from SQL back into `seen_jobs.json` in CP15.2. Reverse writes would create an uncontrolled second writer for the scraper state machine and could overwrite fingerprints, verification timestamps, processing states, or scores.

### 3.2 What SQL owns versus what the pipeline owns

| Data category | Authoritative owner | Sync behavior |
|---|---|---|
| `stable_id` | Pipeline identity algorithm | Insert once; never recompute or mutate in SQL |
| URL, title, company, location, arrangement, salary, description | Pipeline canonical/live data | Upsert from pipeline when present |
| fingerprint and previous fingerprint | Pipeline | Replace from source; do not derive a second fingerprint in SQL |
| processing state | Pipeline state machine | Mirror exactly; SQL does not transition states |
| verification/block/change/closure timestamps | Pipeline | Mirror exactly; preserve source nulls deliberately |
| score, verdict, evaluation, strengths, gaps | Pipeline scoring | Mirror from source; no SQL-side re-scoring |
| rank and rank date | Pipeline ranking | Mirror from authoritative final ranking output |
| saved/viewed/interested/dismissed state | User database | Only `user_jobs` changes it |
| application status, timeline, notes, documents | User database | Only `applications` changes it |
| application company/role snapshot | Application creation flow | Never rewrite from later scraper changes |
| sync metadata and imported-at timestamp | SQL sync layer | Set by sync transaction |

### 3.3 Global jobs versus user-owned records

A single global `jobs` row represents the latest pipeline view of one `stable_id`. It is not a user-owned job and must not contain `user_id`.

`user_jobs` and `applications` continue to reference `job_stable_id` as a logical reference. The first migration should **not** add a foreign key constraint because existing rows can legitimately refer to jobs that are absent from the current JSON dataset, and application history must remain readable even after a posting disappears.

A foreign key can be considered only after a separate data-integrity audit proves that all existing references have corresponding retained/tombstoned `jobs` rows and that deletion semantics are explicitly defined.

## 4. Proposed `jobs` Table

### 4.1 Identity and lifecycle columns

The table should use the pipeline stable ID as its primary key:

| Column | Type | Nullability | Source/meaning |
|---|---|---:|---|
| `stable_id` | `String(64)` | not null, PK | SHA-256 stable identifier |
| `source_key` | `String(255)` | nullable | Current top-level key from `seen_jobs`; diagnostic only |
| `portal` | `String(100)` | nullable | Portal/source name |
| `processing_state` | enum or `String(32)` | not null | Pipeline state such as `ACTIVE_VERIFIED`, `STALE`, `CLOSED_OR_EXPIRED` |
| `status` | `String(64)` | nullable | Legacy/source status such as `discovered` |
| `first_seen` | `DateTime` or ISO text | nullable | First pipeline observation |
| `last_verified` | `DateTime` or ISO text | nullable | Last successful/attempted verification as defined by source |
| `blocked_at` | `DateTime` or ISO text | nullable | 403 block timestamp |
| `blocked_reason` | `String(100)` | nullable | For example `http_403` |
| `changed_at` | `DateTime` or ISO text | nullable | Material change timestamp |
| `closed_at` | `DateTime` or ISO text | nullable | Closure/expiration timestamp |
| `last_active_at` | `DateTime` or ISO text | nullable | Retention input |

Use SQLAlchemy-compatible portable types. A string representation for processing states is preferable in the first migration because the pipeline already owns the state vocabulary and may evolve independently of SQL enum types. If a database enum is used, migrations must be generated for both SQLite and PostgreSQL behavior.

### 4.2 Job content columns

| Column | Type | Nullability | Source/meaning |
|---|---|---:|---|
| `title` | `String(500)` | not null | Canonical title |
| `company` | `String(500)` | not null | Canonical company |
| `location` | `String(500)` | nullable | Normalized location |
| `salary` | `String(255)` | nullable | Original/normalized salary text |
| `url` | `String(2000)` | not null | Canonical URL |
| `arrangement` | `String(32)` | nullable | `remote`, `hybrid`, `onsite`, or `unspecified` |
| `work_mode` | `String(64)` | nullable | Source work-mode detail |
| `description` | `Text` | nullable | Verified/canonical description |
| `fingerprint` | `String(64)` | nullable | Current material-content fingerprint |
| `previous_fingerprint` | `String(64)` | nullable | Prior material-content fingerprint |
| `changed_fields` | `Text` or JSON | nullable | JSON array of changed field names |

The first implementation should retain original salary text rather than parse it into a new salary model. Salary parsing is pipeline logic and is outside CP15.2.

### 4.3 Scoring and ranking columns

| Column | Type | Nullability | Source/meaning |
|---|---|---:|---|
| `rank_score` | `Integer` | nullable | Final ranking score |
| `rank_verdict` | `String(100)` | nullable | Final ranking verdict |
| `rank_date` | `DateTime` or ISO text | nullable | Ranking timestamp/date |
| `fit` | `String(32)` | nullable | Quick fit level |
| `priority_tier` | `Integer` | nullable | Verification priority tier |
| `strengths` | `Text` or JSON | nullable | JSON array |
| `gaps` | `Text` or JSON | nullable | JSON array |
| `evaluation` | `Text` or JSON | nullable | Full scoring evaluation object |

For SQLite/PostgreSQL portability, JSON arrays/objects may initially be stored as serialized JSON text. The backend response layer can deserialize them into the existing Pydantic fields. Native JSON columns are acceptable only if the project standardizes serialization and migration behavior for both dialects.

### 4.4 Sync metadata columns

| Column | Type | Nullability | Meaning |
|---|---|---:|---|
| `source_updated_at` | `DateTime` or ISO text | nullable | Most recent source timestamp available from pipeline data |
| `synced_at` | `DateTime` | not null | Time this row was last successfully synchronized |
| `sync_run_id` | `String(64)` | nullable | CP15 run ID that produced the row |
| `source_schema_version` | `String(32)` | nullable | Input schema/version if available |
| `is_tombstone` | `Boolean` | not null, default false | Retained row no longer present in active source input |

Recommended indexes:

- `processing_state`;
- `(processing_state, rank_score)`;
- `portal`;
- `last_active_at`;
- `sync_run_id`;
- `url` only if a non-unique lookup index is useful.

Do not make `url`, company/title, or source key unique. Stable ID is the only identity guaranteed by the pipeline.

## 5. Field Mapping Rules

### 5.1 Source precedence

For each stable ID, construct one input record using this precedence:

1. `seen_jobs.json` for lifecycle, verification, fingerprint, scoring, and ranking fields;
2. `canonical_jobs.json` for missing core content fields;
3. an authoritative final ranking artifact only for rank fields if the orchestrator explicitly records that artifact as the run output;
4. never infer missing values from `job_search_tracker.csv` or application snapshots.

A value that is explicitly present as `null` in the authoritative source must not be replaced with stale SQL data unless the field-level rule below permits preservation of the last known value.

### 5.2 Update policy by field class

**Replace on source presence:** title, company, location, salary, URL, portal, arrangement, work mode, description, fingerprint, processing state, score, rank, verification/change/closure fields.

**Preserve historical SQL value when source is absent rather than explicitly null:** `source_key`, `sync_run_id`, and audit metadata only.

**Never update from job sync:** `user_jobs.status`, `user_jobs.notes`, `applications.*`, or any document path.

The sync must distinguish “field not included in this source projection” from “field included and null.” A full `seen_jobs` record is expected to be the normal input; partial projections should be rejected or explicitly marked as partial rather than silently clearing data.

### 5.3 Stable ID validation

Before any write:

- require exactly 64 hexadecimal characters;
- reject records whose `stable_id` is missing or malformed;
- reject duplicate stable IDs in the normalized input unless all duplicates are byte-for-byte equivalent after source merge;
- never use the portal key as a replacement stable ID;
- report rejected records in the dry-run and sync summary.

A malformed record must not partially update an existing row.

## 6. Conflict and Deletion Rules

### 6.1 Pipeline versus SQL conflicts

The pipeline wins for all global job fields. SQL is a mirror, not a competing editor.

If SQL contains a newer `synced_at` but the incoming pipeline record has a valid new `sync_run_id`, update the row. `synced_at` is synchronization metadata, not source freshness.

If a source record has an older `last_verified` than SQL, do not invent a merge. Treat the input as stale and either:

- skip the update and report a source-ordering conflict; or
- replace the full pipeline-owned projection only when the run has been proven to be the authoritative run.

The recommended first implementation is to require a run-level input manifest containing `run_id`, completion status, mode, and source paths. A sync without a completed `ranking_report` checkpoint must fail closed.

### 6.2 Records absent from the current input

Absence from one incremental run is not proof that a job was deleted. Do not hard-delete rows merely because they are absent from the current file.

Use this policy:

- active source records are upserted and `is_tombstone = false`;
- records explicitly marked `CLOSED_OR_EXPIRED` remain queryable with that state;
- records absent from a full authoritative snapshot may be marked `is_tombstone = true` only when the input manifest declares a complete snapshot;
- records absent from an incremental input are left unchanged;
- tombstones are never physically deleted by the sync;
- applications and saved-job rows remain intact regardless of source presence.

### 6.3 Application protection

“Application protected” means user history must survive global job changes or disappearance. It does **not** mean an application freezes the global job's title, salary, rank, or processing state forever.

For a job with an `applications` row:

- keep the global `jobs` row even if the source marks it closed or it disappears from a complete snapshot;
- retain the latest pipeline fields and set `is_tombstone` only according to the full-snapshot rule;
- never overwrite `applications.company`, `applications.role`, status, notes, timestamps, or document paths;
- never delete `user_jobs` or `applications` as part of sync;
- preserve enough global data for the application detail endpoint to remain useful.

For a job with only a `user_jobs` row, preserve the global row while it is referenced. The saved-job endpoint already handles unavailable jobs honestly, so deletion is not needed to represent source disappearance.

### 6.4 Concurrent writers

The sync must use a single-writer lock at the process level and a database transaction at the storage level. A second sync started while one is active should exit with a clear “sync already in progress” result, not merge concurrently.

The pipeline itself currently writes JSON files. CP15.2 must run only after the orchestrator has completed the ranking/report stage; it must not read files while a pipeline stage is mutating them.

## 7. Transaction Strategy

### 7.1 Recommended implementation language

Use Python with the existing backend SQLAlchemy layer rather than a Node-only SQLite driver.

Recommended split:

- `backend/app/services/job_sync.py`: reusable sync service with validation, normalization, upsert, dry-run diffing, and reconciliation;
- `job_scraper/sync_to_db.py`: thin CLI entry point that loads pipeline files and invokes the service;
- optional later integration from `orchestrator.js` after the final stage, calling the Python CLI only after a successful checkpoint.

This avoids implementing separate SQLite and PostgreSQL SQL dialects in JavaScript and reuses the existing async engine, settings, models, migrations, and transaction handling.

### 7.2 Transaction boundaries

1. Acquire the single-writer lock.
2. Load and validate the completed pipeline manifest/checkpoint.
3. Read all source files into memory before opening the write transaction.
4. Normalize and deduplicate the complete input set.
5. In dry-run mode, compare input with SQL and exit without writes.
6. Open one database transaction.
7. Upsert all `jobs` rows in deterministic stable-ID order.
8. Apply full-snapshot tombstone handling only when explicitly authorized by the manifest.
9. Insert a sync-run audit record if such a table is included in the implementation scope; otherwise log the summary atomically with the run metadata.
10. Commit once.
11. Re-open a read transaction and perform count/reconciliation checks.
12. Release the lock.

On any validation or database error, roll back the entire transaction. Do not leave a partially synchronized active set.

### 7.3 SQLite and PostgreSQL behavior

The service must use SQLAlchemy expressions and bind parameters, not hand-built SQL strings. SQLite testing should use the same SQLAlchemy model metadata and async driver as the application. PostgreSQL should be tested against a real PostgreSQL service in CI or an explicitly provisioned integration environment.

SQLite's write locking makes the single-writer lock especially important. PostgreSQL can additionally use a transaction-level advisory lock in a future hardening pass, but the portable application lock remains required for cross-process coordination.

### 7.4 Atomicity versus large datasets

The expected dataset is large enough to require deterministic batching for memory and progress, but a single transaction is still preferred for correctness. If batch writes become necessary:

- use one transaction containing all batches;
- checkpoint only outside the SQL transaction;
- never report sync success until the final commit and reconciliation complete;
- on failure, roll back all batches rather than resuming with an unknown partial mirror.

## 8. Migration Plan

### 8.1 Required migration

Add a new Alembic revision after the current head that creates the global `jobs` table and its indexes. The migration must be reversible and must not alter `user_jobs` or `applications` in the first version.

The migration should:

- create `jobs` with `stable_id` as the primary key;
- use portable SQLAlchemy types;
- create indexes needed by active/ranked job queries;
- set safe defaults for `is_tombstone` and `synced_at` handling;
- define downgrade as dropping only the new table and its indexes.

Do not add an FK from `user_jobs.job_stable_id` or `applications.job_stable_id` in this migration.

### 8.2 Initial backfill

The first sync after migration should be explicitly invoked as a backfill, not silently mixed into a normal incremental run:

1. apply the migration;
2. validate the current `seen_jobs.json` and canonical/ranking inputs;
3. run `sync_to_db.py --dry-run --full-snapshot`;
4. review insert/update/reject/tombstone counts;
5. run `sync_to_db.py --full-snapshot`;
6. verify stable-ID count, active-state count, rank coverage, and application-reference coverage;
7. switch backend reads only in a later approved checkpoint.

No existing JSON file should be rewritten by the backfill.

### 8.3 Existing database compatibility

The application currently calls `Base.metadata.create_all()` in tests and development paths, while production-style schema evolution uses Alembic. The implementation must update the SQLAlchemy model and migration together. It must not rely on `create_all()` to alter an existing database, because `create_all()` does not add missing columns/tables safely to a deployed schema.

## 10. CLI Contract

The future sync CLI should expose an explicit, testable contract similar to:

```text
python job_scraper/sync_to_db.py --dry-run
python job_scraper/sync_to_db.py --run-id <completed-run-id>
python job_scraper/sync_to_db.py --full-snapshot --dry-run
```

Required behavior:

- default mode consumes the authoritative incremental output;
- `--dry-run` performs all validation and diff calculation but commits nothing;
- `--full-snapshot` is required before absence-based tombstoning;
- an incomplete/failed checkpoint is rejected;
- malformed stable IDs are reported and cause a non-zero exit unless an explicit future `--allow-rejects` policy is approved;
- the summary includes inserted, updated, unchanged, rejected, tombstoned, application-protected, and final-count values;
- the command exits non-zero on validation, lock, transaction, or reconciliation failure.

Example summary:

```text
CP15.2 DATABASE SYNC
- Run: 20260910-120000
- Mode: INCREMENTAL
- Input records: 261
- Inserted: 12
- Updated: 31
- Unchanged: 218
- Rejected: 0
- Tombstoned: 0
- Application-protected: 7
- SQL jobs after sync: 261
- Reconciliation: PASS
```

## 11. Test Strategy

### 11.1 Required unit tests

1. **Input shape normalization**
   - unwrap `{seen: {...}}` correctly;
   - reject non-object records;
   - preserve stable IDs from records rather than source keys.

2. **Stable ID validation**
   - accept a valid 64-character lowercase/uppercase hexadecimal ID;
   - reject missing, short, non-hex, and duplicate IDs;
   - never generate a replacement ID during sync.

3. **Field mapping**
   - map all core, lifecycle, scoring, ranking, and JSON fields;
   - merge missing core fields from canonical input;
   - preserve application snapshots independently.

4. **Idempotency**
   - first sync inserts;
   - second identical sync produces only unchanged rows;
   - repeated sync does not create duplicates.

5. **Update behavior**
   - changed score/state/content updates the global row;
   - source null handling follows the declared policy;
   - stale input is rejected or reported, not silently merged.

6. **Application protection**
   - a closed/absent source job remains queryable when an application references it;
   - application status, notes, snapshots, timestamps, and document paths are unchanged;
   - user saved rows are unchanged.

7. **Incremental versus full snapshot**
   - incremental absence leaves rows unchanged;
   - full snapshot can mark absent rows as tombstones;
   - tombstoning never deletes rows.

8. **Dry run**
   - reports inserts/updates/tombstones;
   - performs no SQL writes;
   - does not modify JSON files.

9. **Transaction rollback**
   - a failure in the middle of a sync leaves no partial jobs table changes;
   - lock is released after failure.

10. **Reconciliation**
    - final SQL count matches normalized input under incremental/full-snapshot rules;
    - active-state and rank coverage checks detect missing rows or scores.

### 11.2 Integration tests

Run the same service tests against:

- SQLite with `aiosqlite`;
- PostgreSQL with a real test database.

Do not rely only on SQLite because upsert syntax, transaction locking, enum behavior, and JSON handling can differ by dialect.

### 11.3 Backend compatibility tests

After sync implementation, verify that a DB-backed read path returns the same `JobRecord` fields as the current JSON-backed `DataStore` for a fixture set containing:

- active verified job;
- blocked active-unverified job;
- changed job;
- closed job;
- job with an application;
- job with a saved-job association;
- job absent from the latest incremental input.

## 12. Rollback Strategy

### 12.1 Code/schema rollback

- Revert the application code change first if the new DB read path causes regressions.
- Keep the `jobs` table in place while diagnosing data issues; reverting the migration is a separate, explicit operation.
- Use the Alembic downgrade only when the table is no longer needed and a verified backup exists.
- Never use destructive database reset commands as a recovery shortcut.

### 12.2 Data rollback

Before each non-dry-run sync:

- record the input run ID and normalized input hash;
- record pre-sync counts and affected stable IDs;
- write a sync audit record or an external JSON manifest containing the diff;
- create a database backup/snapshot according to the deployment environment.

If a sync is incorrect, restore the `jobs` mirror from the last verified DB backup or replay the prior normalized input through the same transactional sync service. Do not “repair” the pipeline by editing `seen_jobs.json` from SQL values.

### 12.3 Source rollback

Pipeline JSON remains independently recoverable through its existing checkpoint and backup conventions. A database rollback must not change `seen_jobs.json`, canonical files, checkpoints, tracker CSV, applications, or saved-job rows.

---

## 13. Operational Gates Before Implementation

CP15.2 implementation should not begin until these decisions are accepted:

- `seen_jobs.json` is the authoritative incremental sync input;
- the final ranking artifact contract is explicit and no longer ambiguous between `seen_jobs.json`, `ranked_jobs.json`, and dated ranking files;
- a global `jobs` table is approved as a schema addition;
- Python/SQLAlchemy is approved for SQLite/PostgreSQL portability;
- application and saved-job rows remain independent and are never deleted by sync;
- full-snapshot tombstoning is opt-in;
- database backup and lock behavior are available in the deployment environment;
- CP15.2 remains separate from scheduler, monitoring, portal health, API read migration, and frontend changes.

---

## 14. Final Recommendation

Implement CP15.2 as a **one-way, transactional mirror** rather than a bidirectional database sync:

```text
seen_jobs.json + canonical/ranking projections
            → validate/normalize
            → transactional upsert
            → jobs table
```

Do not attempt to sync directly into `UserJob` or `Application`; those tables model user actions, not global job data. Do not add a jobs-table foreign key until orphan-reference handling is proven. Do not delete absent jobs. Do not allow SQL to become a second writer for pipeline state.

The smallest safe implementation is a new `jobs` model and migration, a SQLAlchemy-based sync service/CLI, dry-run and reconciliation tests, and no backend read-path cutover until the mirror has passed backfill and compatibility validation.
