# CP15.4 Progress Monitoring & Notifications — Implementation Report

**Date:** 2026-09-11
**Status:** COMPLETE — implementation, tests, and read-only validation passing
**Scope:** Non-invasive progress monitor + run-history recorder reading existing checkpoint/ranking artifacts. No modifications to orchestrator, scheduler, sync, pipeline scripts, or any data schemas.

---

## Executive Summary

Implemented `job_scraper/monitor.js` (the run-history recorder and progress monitor), `job_scraper/run_history.json` (persistent per-run records), and `job_scraper/monitor.test.js` (22 targeted tests).

The monitor is **non-invasive**: it observes the pipeline's existing state through `checkpoints.json`, `top5_jobs.json`, and `seen_jobs.json` and never touches the orchestrator or its outputs. It reconstructs the 7 orchestrator stages, derives an overall SUCCESS/FAIL status without inventing state, builds ONE shared summary object used for both the persistent run-history record and the completion/failure notification, and records it idempotently by `run_id`.

Notifications are isolated behind an injectable notifier. Because `PushNotification` is a **Claude Code session tool, not a Node.js API**, the monitor can never create live scheduled notifications; the default notifier degrades gracefully (WARN + continue) whenever the interface is unavailable, which is the normal case in Node.

## Scope Boundary (what was NOT done)

- **No orchestrator changes.** `monitor.js` does not hook `writeCheckpoint`, read live in-flight stage boundaries, or modify `orchestrator.js`. Stage-boundary progress is reconstructed from checkpoint data already present in `checkpoints.json`.
- **No live per-stage notifications.** Each run's completion/failure is the notification point; the notification payload carries the reconstructed stage context.
- **No portal health thresholds or rolling history.** `portal_health` in the summary contains only portal/blocked evidence already present in pipeline outputs (`seen_jobs.json` blocked records, or orchestration `blocked` counts as fallback). No `portal_health.json` was created and no `SKILL.md` `enabled` flags were touched — those belong to CP15.5.
- **No timing fabrication.** `duration_ms` is derived only from valid existing checkpoint timestamps (`started_at` → per-stage `last_updated`). When a timestamp is absent or invalid, `duration_ms` is `null`.
- **No real CronCreate/notification jobs created.** The notification interface is mocked in tests; the real default notifier only emits a WARN.

## Architecture

### Inputs (read-only)

| Artifact | Use |
|---|---|
| `job_scraper/checkpoints.json` | Source of truth: `current_checkpoint` (run_id, mode, counts) + flat `run_history[]` (per-stage entries with `stage`, `stage_status`, `last_updated`, counts) |
| `job_scraper/top5_jobs.json` | Ranked top-5 array for the summary's `top_5` block |
| `job_scraper/seen_jobs.json` | Per-portal blocked evidence (`blocked_reason` + `blocked_source`/`portal`) for `portal_health` |

### Processing steps

1. **Load** — parse and validate `checkpoints.json` (missing file, malformed JSON, missing both `current_checkpoint`/`run_history` all fail safely with a clear error).
2. **Identify run** — prefer `current_checkpoint.run_id`; a CLI `--run-id` must exist in `run_history`; else fall back to the most recent `run_history` entry by `last_updated`.
3. **Reconstruct 7 stages** — iterate the exact orchestrator stage vocabulary `discovery → canonicalization → hard_filter → priority_queue → verification → scoring → ranking_report`. For each stage record a `{status, started_at, completed_at, duration_ms, counts}` object. Stages with no checkpoint entry are `not_run`. Non-orchestrator legacy stage names are ignored. A later duplicate entry for the same stage wins (terminal state). Because the orchestrator pushes only `complete`/`failed` stage records to `run_history`, the **in-progress stage lives only in `current_checkpoint`** — when that stage has no history entry yet, it is seeded from `current_checkpoint` so an interrupted run reports its live stage instead of `not_run`.
4. **Derive status** — `SUCCESS` only when `ranking_report` is `complete`; anything short (failed, in-progress) is `FAIL`, with the first non-terminal/`not_run` stage located for the failure context.
5. **Extract counts** — aggregate numeric counts (jobs_processed, total, batch, passed, deprioritized, queue_length, verified, blocked, changed, closed, top5/top10 counts). Counts are **run-scoped**: the terminal `current_checkpoint` snapshot is overlaid only when it belongs to the monitored `run_id`; a historical `--run-id` derives counts from its own stage records only, so it never inherits another run's numbers.
6. **Build ONE summary object** — `{run_id, started_at, completed_at, mode, status, stages, counts, top_5, portal_health}`. This single object is the input to both persistence and notification, so the run-history record and the notification always agree.
7. **Notify** — via the injectable notifier: `completion` on SUCCESS, `failure` (with `failed_stage` + error context) on FAIL.
8. **Persist idempotently** — `upsertRun` replaces any existing record with the same `run_id` in `run_history.json`; it never writes a duplicate. Atomic write (temp file + rename).

### 7-stage vocabulary (exact orchestrator names)

`discovery`, `canonicalization`, `hard_filter`, `priority_queue`, `verification`, `scoring`, `ranking_report`

### Idempotency
`upsertRun` is a deterministic replace-on-`run_id`. Re-running the monitor for the same run produces exactly one entry and updates that entry in place. `persistRunHistory` recreates the file with the base schema if it is absent or malformed.

## Notification Abstraction

`monitor.js` accepts an optional `notifier` function (`makeNotifier`). The notifier is invoked with `('completion' | 'failure', payload)`. The payload always carries a `run_id`, the formatter text (`summary`), and the shared summary object (`summaryObject`); the failure payload additionally carries `failed_stage` and `context` (checkpoint `error` if present, else the first non-terminal stage's terminal state).

The **default notifier** (`defaultNotifier`) does NOT attempt to call `PushNotification` — that is a Claude Code session tool with no Node API. It logs a WARN (`PushNotification unavailable in Node runtime; <kind> notification for run <id> not sent`) and returns `{sent: false, unavailable: true}`. The monitor completes successfully. Tests substitute a mock notifier to verify the call contract without any real dependency. This means: **live notifications are impossible from the Node CLI by design; the injection point is where a Claude Code host integration or future connector would plug in.**

## Portal-Health Boundary

`portal_health` is an **evidence summary, not a diagnostic**. It reports, per portal, the count of records in `seen_jobs.json` carrying a `blocked_reason` (grouped by `blocked_source`/`portal`, top 10). If that read fails or is empty but orchestration `blocked` count is present, a fallback `{note, blocked_total}` entry is emitted. No thresholds, no rolling history, no auto-disable, and no `SKILL.md` mutation — all CP15.5 scope.

---

## Duration Derivation

`duration_ms` for a stage = `last_updated(stage) − started_at(run)` when both are valid ISO timestamps and the delta is non-negative; otherwise `null`. Only the pipeline's own persisted timestamps are used, and the anchor is the run's `started_at`. When `current_checkpoint` lacks a fresh timestamp, earlier stages report `null` rather than fabricated values. `completed_at` is the injected stage's `last_updated` in ISO form.

## Issues & Deviations

1. **Notifier is unavailable by design in Node.** CP15.4's original deliverable "PushNotification at run completion/failure" is impossible to call directly from a Node CLI (PushNotification is a Claude Code session tool). The monitor implements the call contract behind an injectable notifier and degrades to WARN when unavailable — the hardest guarantee it can honor from pure Node. Live notifications remain a Claude Code host responsibility (mirroring the CP15.3 CronCreate finding).

2. **Reconstructed (not live) stage progress.** Because the orchestrator was not modified, stage boundaries are reconstructed from persisted checkpoint records rather than observed in-flight. This means partial-run progress reflects the last persisted state per stage, which is the correct non-invasive behavior. To keep interrupted runs accurate, the live stage is seeded from `current_checkpoint` (see Architecture step 3).

3. **Durationms null where timestamps are invalid.** Real historical runs may carry inconsistent timestamps; the monitor never invents a duration. This is a deliberate data-integrity choice.

4. **`run_history.json` currently empty.** Initialized as `{"schema_version":"1.0","runs":[]}`. The monitor populates it on the next non-dry-run invocation. No real run was persisted during this checkpoint to preserve the read-only validation boundary.

5. **Two behavior corrections surfaced during read-only validation** (both caught before any real writes):
   - **`current_checkpoint` seeding** — the terminal `--dry-run` against real `checkpoints.json` succeeded because that run's stage records exist; a hypothetical run whose only in-progress evidence lived in `current_checkpoint` would have rendered every stage `not_run`. `reconstructStages` now seeds the live stage from `current_checkpoint` when no history entry exists for it.
   - **Run-scoped counts** — `--run-id 20260824100000` initially inherited the current run's aggregate counts (`passed: 123`, etc.) from `current_checkpoint`. `extractCounts` now overlays the terminal snapshot only when `current_checkpoint.run_id` matches the monitored run; historical runs report their own stage counts. Test `extractCounts overlays current_checkpoint only for the monitored run` locks this behavior.
