## 3. END-TO-END FLOW AUDIT

### Admin Job Source Lifecycle Flow

```
URL Entry (/admin/sources → "Add Source" modal)
    │
    ├─→ Admin enters: Name, Display Name, Base URL, Source Type
    │
    ├─→ POST /api/admin/sources → Creates JobSource (status=DISCOVERED, enabled=false)
    │
    ├─→ Admin clicks "Analyze" button on source row
    │       │
    │       └─→ POST /api/admin/sources/{id}/analyze
    │               │
    │               ├─→ Updates status to ANALYZING
    │               ├─→ Calls analyze_url(source.base_url)
    │               │       ├─→ SSRF validation (hostname/IP checks)
    │               │       ├─→ HTTP GET with manual redirect handling (max 3)
    │               │       ├─→ Content-Type guard (text/html only)
    │               │       ├─→ 2MB response limit
    │               │       ├─→ HTML parsing (BeautifulSoup)
    │               │       │       ├─→ Title, meta description
    │               │       │       ├─→ Platform detection (11 signatures)
    │               │       │       ├─→ Search form detection
    │               │       │       ├─→ Pagination link detection
    │               │       │       ├─→ JSON-LD JobPosting/ItemList
    │               │       │       └─→ robots.txt fetch & analysis
    │               │       └─→ Feasibility assessment
    │               │
    │               ├─→ Stores analysis_data on source
    │               ├─→ Updates status to READY_FOR_REVIEW
    │               └─→ Returns analysis to UI (modal with feasibility badge)
    │
    ├─→ Admin reviews analysis in Detail modal
    │       │
    │       ├─→ If viable: Clicks "Edit" → PATCH status=APPROVED
    │       │       └─→ Developer implements CLI skill (manual, outside app)
    │       │       └─→ Developer registers in portal_registry.PORTAL_BASE_TO_SKILL
    │       │       └─→ Admin sets adapter_name (e.g., "indeed-search")
    │       │       └─→ Admin PATCH enabled=true → Status becomes ENABLED
    │       │
    │       └─→ If not viable: Clicks "Delete" → DELETE (allowed only if not ENABLED/APPROVED)
    │
    └─→ Source now appears in portal health monitoring (CP15.5/15.6)
            └─→ Health engine tracks access success/403 rates
            └─→ Auto-disables if >50% 403s in 7-day window
            └─→ Frontend /health page shows status
```

| **CP15.6 Health API** | **INTEGRATION POINT** — `/api/health/portals` exposes `skill_enabled` from SKILL.md; CP16 `JobSource.enabled` is separate but should align | ⚠️ **MANUAL BRIDGE** | Two sources of truth for "enabled" — **GAP** |
| **Portal Registry** | CP16 `JobSource.adapter_name` should match `PORTAL_BASE_TO_SKILL` values | ✅ **ALIGNED** | Both use skill names (e.g., "indeed-search") |
| **Scraper Skills** | CP16 expects developer to create `.agents/skills/{name}-search/` | ✅ **CLEAN BOUNDARY** | No auto-generation of scraper code |

### Critical CP15/CP16 Boundary Gaps

1. **CP15.5 auto-disable → CP16 JobSource sync missing**: When CP15.5 disables a portal via SKILL.md, the corresponding `JobSource.enabled` remains `true` in the database. No webhook, event, or polling mechanism exists to synchronize.

2. **Dual "enabled" sources of truth**: 
   - CP15.5: SKILL.md `enabled` key (source of truth for orchestrator)
   - CP16: `JobSource.enabled` column (source of truth for admin UI)
   These can diverge with no reconciliation.

3. **CP15.6 health API reads SKILL.md, not JobSource**: The `/api/health/portals` endpoint reads `skill_enabled` from SKILL.md frontmatter, not from `JobSource.enabled`. Admin enabling a source in UI doesn't immediately reflect in health API until SKILL.md is manually updated.

## 8. IDENTIFIED GAPS REQUIRING FOLLOW-UP

### Gap 1: CandidateProfile.full_name Not Auto-Initialized on Registration
- **Spec:** CP16.1 Section 2.3: "When a user registers, auth.register writes User.name AND automatically initializes CandidateProfile with full_name = user.name"
- **Actual:** `auth.py:96-130` creates `User` but does NOT create `CandidateProfile`
- **Impact:** New users have `User.name` but empty `CandidateProfile.full_name` — breaks CV generation pipeline
- **Fix:** In `register()` after `session.commit()`, create `CandidateProfile(user_id=user.id, full_name=user.name)`

### Gap 2: CP15.5 Auto-Disable Does Not Sync to JobSource.enabled
- **Spec:** CP16.1 Section 5.2 Bridge: "Health engine (CP15.5) monitors error rates → DB JobSource status updated to ENABLED"
- **Actual:** CP15.5 writes `enabled:false` to SKILL.md only; `JobSource.enabled` column unchanged
- **Impact:** Admin UI shows source as "Enabled" (green) while orchestrator skips it; health API shows disabled
- **Fix:** Option A: CP15.5 emits event / writes to DB; Option B: CP16 adds periodic sync job; Option C: Health API reads JobSource.enabled

### Gap 3: No Tests for Admin Users Endpoint
- **Spec:** CP16.1 Section 9.1: "End-to-End Regression Suite — Run existing test suites"
- **Actual:** `test_rbac_auth.py` has no tests for `/api/admin/users`
- **Impact:** Unverified admin user listing, search, filter functionality
- **Fix:** Add `TestAdminUsersList` class in `test_rbac_auth.py`
