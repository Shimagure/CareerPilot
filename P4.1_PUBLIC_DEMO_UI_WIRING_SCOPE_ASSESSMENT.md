## Executive Summary

This assessment maps the current frontend data-bearing pages to their API consumption patterns, classifies each page as public/private compatible, identifies gaps for wiring public demo pages to `/api/public/*` endpoints, and designs a test plan for validation. **No code changes are made in this phase.**

The expanded P4 demo dataset (56 jobs, 16 applications, rich evaluations, checkpoints) is already served via `/api/public/*` endpoints. The frontend currently uses a mix of public and private API calls depending on the page and hook. This assessment provides the complete wiring map.

## 3. Auth Context & Routing Analysis

### 3.1 `AuthContext.tsx` — Token Management
- Token stored in `localStorage['careerpilot_token']`
- Axios interceptor injects `Authorization: Bearer <token>` on **all** requests
- 401 response → clears token + dispatches `careerpilot:unauthorized` event
- `login`/`register` set token; `logout` clears token + calls `/api/auth/logout`

**Implication:** Even public endpoint calls will carry the auth header if a token exists. Backend `/api/public/*` routes must accept (but not require) auth and serve demo data regardless.

### 3.2 `ProtectedRoute.tsx` & `AdminRoute.tsx`
- `ProtectedRoute`: Redirects to `/login` if `!isAuthenticated` (checks `token && user`)
- `AdminRoute`: Adds `user?.role === 'admin'` check
- All app routes except `/login`, `/register` wrapped in `ProtectedRoute`

**Implication:** Public demo pages **cannot** be accessed without authentication under current routing. Options:
1. Create public demo routes outside `ProtectedRoute` (e.g., `/demo/dashboard`, `/demo/jobs`)
2. Add a "public demo mode" flag that bypasses auth check for specific routes
3. Use `DemoModeContext` to conditionally render public data when demo mode active

### 3.3 `DemoModeContext.tsx` & `DemoModeBanner.tsx`
- `isDemoMode` state (boolean), `demoStatus` from `/api/demo/status`
- `bootstrapDemo()` → `POST /api/demo/bootstrap` (auth required)
- `resetDemo()` → `POST /api/demo/reset` (auth required)
- `DemoModeBanner` shows when `isDemoMode=true`, offers "Re-bootstrap" / "Exit Demo Mode"
- Sidebar shows demo toggle switch

**Current behavior:** Demo mode is an **authenticated** feature — user must log in first, then enable demo mode. This is different from "public demo" (unauthenticated access).

### 3.4 `App.tsx` Routing Structure
```
/login, /register                    → Public (no auth)
/dashboard, /jobs, /jobs/:id, /jobs/:id/fit,
/ranked, /assistant, /saved-jobs, /applications,
/pipeline, /health, /retention, /resume,
/profile, /preferences, /search       → ProtectedRoute (auth required)
/admin/sources, /admin/users          → AdminRoute (auth + admin)
/                                     → Redirect to /dashboard
```

**No public demo routes exist.**

## 5. FitAnalysis & Applications Compatibility Deep-Dive

### 5.1 FitAnalysis (`/jobs/:stable_id/fit`)
- **Reads:** `useJob(stable_id)` → `/api/jobs/{id}` (private)
- **Data needed:** `job.evaluation` (technical, experience, behavioral, career, overall, verdict, key_strengths, gaps, recommendation, evaluated_at)
- **Public equivalent:** `GET /api/public/jobs/{id}` **returns full JobRecord including evaluation** (verified in `test_demo_data.py::test_public_job_detail_includes_evaluation`)
- **Gap:** Hook uses private `jobsApi.get` → `apiClient.getJob` → `/api/jobs/{id}`
- **Fix:** Create `usePublicJob(stable_id)` hook calling `apiClient.getPublicJob(stable_id)`

### 5.2 Applications (`/applications`)
- **Reads:** `useApplications()` → `/api/applications` (private, user-scoped)
- **Mutations:** `useUpdateApplication` (PATCH), `useRemoveApplication` (DELETE)
- **Public equivalent:** **None** — applications are inherently user-scoped private data
- **Demo data:** 16 demo applications exist in `demo_tracker.csv` with statuses, notes, fit_ratings, document metadata
- **Gap:** No `/api/public/applications` endpoint exists
- **Design decision:** Public demo should show **read-only** demo applications (simulated portfolio). Mutations disabled in public demo mode.

### 5.3 RankedJobs & JobDetail — Ranked Data
- **Reads:** `useTop5Jobs`/`useTop10Jobs`/`useAllRankedJobs` → `/api/ranked/*` (private)
- **Public equivalent:** **None** — no `/api/public/ranked/*` endpoints
- **Demo data:** 50 active jobs have `rank_score`, `rank_verdict`, `priority_tier`
- **Gap:** Need public ranked endpoints or reuse `/api/public/jobs/active` with client-side sort

## 6. DemoModeContext Integration Points

### Current Flow
1. User logs in (private)
2. User toggles "Demo Mode" in sidebar → `bootstrapDemo()` → `POST /api/demo/bootstrap`
3. `isDemoMode=true` → `DemoModeBanner` shows, sidebar shows "Active — simulated data"
4. **But:** All page hooks still call **private** endpoints (`/api/jobs`, `/api/ranked/*`, etc.)

### Required Changes for Public Demo Wiring
- When `isDemoMode=true`, hooks should switch to public endpoints
- Or: Create parallel "public demo" page variants at `/demo/*` routes
- Or: Add `demoMode` parameter to existing hooks

### Recommended Approach: Context-Aware Hooks
```typescript
// In each hook, check demo mode and switch endpoint
const { isDemoMode } = useDemoMode();
const endpoint = isDemoMode ? '/api/public/jobs/active' : '/api/jobs';
```

## 11. Risk Assessment & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Public endpoints return stale data (corpus ages) | High | Medium | Generator re-run with `--corpus-date` refreshes; document refresh cadence |
| Private hooks accidentally called in public demo | Medium | High | Lint rule: no `/api/` (private) imports in public demo pages; code review |
| Auth token leakage to public endpoints | Low | Medium | Backend ignores auth on `/api/public/*`; frontend clears token for public routes |
| Demo applications show PII | Low | High | P4 leakage scan passed; re-scan before each generator run |
| Ranked endpoints not implemented on backend | Medium | High | Implement minimal `/api/public/ranked/*` or reuse `/jobs/active` with sort |
| Routing conflicts with protected routes | Low | Medium | Use distinct `/demo/*` prefix outside ProtectedRoute |

## 14. Architecture Decisions (Appended per User Directive)

### 14.1 P1 Public API Boundary — Preserved

**Decision:** The public recruiter-facing demo MUST continue using:

```
frontend
  -> /api/public/*
  -> DemoDataStore
  -> backend/demo_data/*
```

**Constraint:** Do NOT introduce a new public `/api/demo/*` or `/demo/*` API namespace.

`/api/demo/*` remains a separate authenticated/internal demo-management plane unless existing architecture proves otherwise.

**Rationale:** P1 established the `/api/public/*` boundary for unauthenticated access. Introducing `/api/demo/*` as a second public namespace creates confusion, duplicates the demo data surface, and weakens the security boundary between "public unauthenticated" and "authenticated demo management."

---

### 14.2 Public Demo Applications — Safe to Expose

**Decision:** Clarify the distinction between:

| Scope | Endpoint | Data Source | Auth |
|-------|----------|-------------|------|
| **PRIVATE** | `/api/applications` | Real user's application tracker (user-scoped) | Required |
| **PUBLIC DEMO** | `/api/public/applications` | Fictional P4 demo applications from `DemoDataStore` / `demo_tracker.csv` | None |

The 16 P4 application records are intentionally fictional demo data and are therefore candidates for the public recruiter experience.

**Do not treat them as real user-scoped application data.**

**Rationale:** The P4 demo corpus explicitly created 16 fictional applications (draft, submitted, under_review, interview, offer, accepted, rejected, withdrawn) for demonstration purposes. These are not linked to any real user account and contain no PII. Exposing them read-only via `/api/public/applications` is safe and valuable for recruiter evaluation.

---

### 14.3 Avoid Unnecessary Page Duplication

**Decision:** Do NOT assume every public page needs a separate `PublicX.tsx` page component.

**Strategy:** Prefer reusing existing components/pages with separate public data hooks/client methods where the presentation is already appropriate.

**Classification of pages:**

| Page | Reuse Strategy | Reason |
|------|----------------|--------|
| **PipelineHealth** | ✅ Reuse existing | Already reads `getPublicPortalHealth()`; no auth-dependent UI |
| **RetentionStats** | ✅ Reuse existing | Already reads `getPublicRetentionStats()`; no auth-dependent UI |
| **Pipeline** | ✅ Reuse existing | `getPublicPipelineStatus()` exists; read-only display |

### 14.4 Minimize New Backend Endpoints

**Decision:** Re-evaluate the proposed four new backend endpoints. For each, document the exact analysis.

| Proposed Endpoint | Frontend Consumer | Existing Endpoint That Cannot Be Reused | Exact Data Required | Why Public Router Cannot Provide It | Prefer Extending Existing? |
|-------------------|-------------------|------------------------------------------|---------------------|-------------------------------------|----------------------------|
| `GET /api/public/ranked/top5` | `PublicDashboard`, `PublicRankedJobs` | `/api/public/jobs/active` | Top 5 jobs by `rank_score` desc with full `JobRecord` | `/api/public/jobs/active` returns paginated list without guaranteed rank order; frontend would need to fetch all 50+ jobs to sort client-side | **YES** — Extend `/api/public/jobs/active` with `?sort=rank_score&order=desc&limit=5` |
| `GET /api/public/ranked/top10` | `PublicRankedJobs` | `/api/public/jobs/active` | Top 10 jobs by `rank_score` desc | Same as above | **YES** — Same extension with `limit=10` |
| `GET /api/public/ranked/all` | `PublicRankedJobs` | `/api/public/jobs/active` | All active jobs sorted by rank_score desc | Same as above | **YES** — Same extension with `sort=rank_score&order=desc` |

3. **Defer** `/api/public/dashboard` — derive client-side from existing public endpoints

### 14.5 Resolve Ranked Jobs Explicitly

**Decision:** **Option B — Derive ranking client-side from the existing public jobs response.**

**Rationale:**
- `/api/public/jobs/active` already returns all 50 active jobs with `rank_score`, `rank_verdict`, `priority_tier` fields (verified in P4 test suite)
- Adding `sort`, `order`, `limit` query parameters to the existing endpoint is a minimal backend change
- Avoids duplicating ranking business logic (sort by `rank_score` desc, tie-break by `priority_tier`, then `evaluated_at`) in a new endpoint
- Frontend `PublicRankedJobs` and `PublicDashboard` can use `usePublicJobs({ sort: 'rank_score', order: 'desc', limit: 5/10 })`

**Backend Change:** Add optional query parameters to `GET /api/public/jobs/active`:
- `sort?: 'rank_score' | 'evaluated_at' | 'created_at'` (default: `evaluated_at` desc for recency)
- `order?: 'asc' | 'desc'` (default: `desc`)
- `limit?: number` (default: 20, max: 100)

### 14.6 Resolve Dashboard Explicitly

**Decision:** Public dashboard shows a **demo-only summary derived from DemoDataStore**, not private user metrics.

**Public Dashboard Widgets (read-only, no auth):**

2. **Top 5 Ranked Jobs** — from `/api/public/jobs/active?sort=rank_score&order=desc&limit=5`

4. **Application Portfolio Summary** — from `/api/public/applications` (counts by status)
5. **Portal Health** — from `/api/public/health/portals` (optional, smaller widget)

**Explicitly Excluded (Private User Metrics):**
- User's personal application count/status
- User's saved jobs count
- User's search run history
- User's resume/profile completion
- User's preferences

**Rationale:** The public recruiter sees a "portfolio view" of the demo system's capabilities, not a personalized dashboard. This avoids any leakage of private user data patterns.

### 14.7 Resolve Authentication/Routing

**Decision:** Create a **new public route wrapper** — `PublicRoute` — that renders without authentication checks.

**Route Classification:**

| Route Pattern | Wrapper | Auth Required | Notes |
|---------------|---------|---------------|-------|
| `/login`, `/register` | None (public) | ❌ | Existing |
| `/demo/*` | `PublicRoute` | ❌ | **New** — all public demo pages |
| `/dashboard`, `/jobs`, `/jobs/:id`, `/jobs/:id/fit`, `/ranked`, `/assistant`, `/saved-jobs`, `/applications`, `/pipeline`, `/health`, `/retention`, `/resume`, `/profile`, `/preferences`, `/search` | `ProtectedRoute` | ✅ | Existing private routes |
| `/admin/*` | `AdminRoute` | ✅ + admin | Existing admin routes |
| `/` | Redirect | ❌ | Redirect to `/login` (not `/demo/dashboard`) |

**PublicRoute Implementation:**
```tsx
// frontend/src/components/PublicRoute.tsx
export function PublicRoute({ children }: { children: React.ReactNode }) {
  // No auth check — renders children directly
  // Optionally: clear any stale token from localStorage for clean public session
  return <>{children}</>;
}
```

**AuthContext Behavior for Public Routes:**
- Axios interceptor injects `Authorization` header if token exists
- Backend `/api/public/*` routes **must accept but ignore** auth header (already the case)
- Frontend should **not** call `getCurrentUser()` on public routes (avoids 401 noise)
- `DemoModeContext` is **not used** for public demo — public demo is a separate unauthenticated experience

**No `demo=true` runtime toggle.** The solution is structural: separate route tree, separate hooks, separate API client methods.
