## 3. Auth / Session Behavior — Before and After

| Aspect | Before | After |
|---|---|---|
| JWT payload | `sub`, `role`, `exp` | `sub`, `role`, `exp`, `token_version` |
| Server-side session invalidation | None (stateless JWTs lived until `exp` or until account status changed) | Per-user `token_version` counter compared on every authenticated request |
| Logout | No-op endpoint; token survived server-side until expiry | Authenticated endpoint; increments `token_version`, invalidating every outstanding token for that account |
| Account deactivation / suspension | `get_current_user` already rejected non-`ACTIVE` accounts live per request | Unchanged (still enforced live per request) — locked with a test |
| Password change / reset | Does not exist in the app | Not built (out of scope); the `token_version` counter is the generic primitive a future password reset would increment |

### 3.1 `get_current_user` enforcement order
1. Missing/malformed `Authorization` header → 401.
2. `decode_token` failure (malformed, expired, wrong signature, `alg:none`, wrong algorithm) → 401 `Invalid or expired token`.
3. Missing `sub` → 401 `Invalid token payload`.
4. User not found → 401.
5. Account not `ACTIVE` → 401 `User account is not active`.
6. `payload["token_version"] != user.token_version` (missing claim also fails) → 401 `Token has been revoked, please sign in again`.

The version claim is checked against the DB value on **every** protected request, so a revocation takes effect immediately — no token-lifetime delay.

## 4. Session Invalidation Mechanism

A per-user integer session version (`token_version`, default 1):

- **Issued:** login/register embed the account's current counter as a `token_version` claim.
- **Enforced:** `get_current_user` (the single dependency behind all protected routes) compares the claim to `user.token_version`; mismatch **or missing claim** → 401 (fail closed). Tokens issued before this change therefore expire immediately on first request — intentional invalidation of the old issuance.
- **Revoked:** incrementing the counter (e.g. logout) invalidates all JWTs previously issued for that account, even ones that are cryptographically valid and unexpired.
- **No blacklist, no server-side token storage** — the counter is the entire revocation state, bounded to one column per user.

**Database:** fresh databases get the column automatically via `Base.metadata.create_all` (`server_default="1"`). The project has no migration tool (schema is created by `create_all`), so existing databases need the one-line statement below. This is the deliberate lightweight choice per scope — no migration infrastructure was introduced.

```sql
ALTER TABLE users ADD COLUMN token_version INTEGER NOT NULL DEFAULT 1;
```

Existing rows default to 1, so all currently-issued JWTs (which lack the claim) are rejected immediately — the intended fail-closed migration behavior.

## 5. Logout Semantics & Frontend Token Storage

**Logout (backend):** `POST /api/auth/logout` now requires authentication and increments the caller's `token_version`, revoking all of that user's outstanding tokens server-side, then returns the existing message (`Successfully logged out`). An unauthenticated logout returns 401 (there is no session to revoke).

**Logout (frontend):** unchanged and already correct — `AuthContext.logout` POSTs `/api/auth/logout` with the Bearer token (set as a global axios default at login), then in a `finally` block removes `localStorage['careerpilot_token']`, nulls token/user state, and deletes the axios `Authorization` header (`frontend/src/context/AuthContext.tsx:120-140`). So server-side revocation *and* full client-state cleanup both occur with zero frontend changes.

**Token storage decision:** the JWT continues to be stored in `localStorage` (key `careerpilot_token`). Moving to `httpOnly` cookies was evaluated and rejected: it is a broad redesign (auth flow, CSRF posture, CORS/proxy) well beyond P3.4's scope. The localStorage risk (P3 MEDIUM finding) is accepted and documented as a residual risk (§8). It is mitigated by: 24/7–30 min token expiry, server-side revocation on logout, and the fact that tokens are never written to logs (audit tests assert no JWT/password text; P3.3).

Centralized in `Settings.validate_production_config()` (called from the FastAPI lifespan, `backend/app/main.py`); any failure raises `ValueError` and aborts startup — **fail closed** with a clear, secret-free error.

### 6.1 Exact `RATE_LIMIT_ENABLED` behavior
- **Production + `RATE_LIMIT_ENABLED=false`** → startup fails with `ValueError`: *"Production environment requires RATE_LIMIT_ENABLED=true. Disabling rate limiting in production is not allowed."* The error names the offending setting without exposing any secret.
- **Production + `RATE_LIMIT_ENABLED=true`** → validation passes; rate limiting active.
- **Development / test + `RATE_LIMIT_ENABLED=false`** → preserved escape hatch (`validate_production_config` returns early for non-production; `test_rate_limit.py::test_rate_limit_can_be_disabled` still green).

## 8. Known Limitations / Residual Risks

- **localStorage JWT storage** (P3 MEDIUM): persists across sessions; XSS on the SPA could exfiltrate it. Mitigations: short expiry, server-side revocation, active timeouts are out of scope. Cookie-based storage deferred.
- **Existing databases** need the one documented `ALTER TABLE` (no migration tool exists; `create_all` won't add the column to an existing table).
- **Tokens issued before this change** are invalidated immediately (missing claim → 401) — intentional, but deployers should expect users to re-login once.
- The counter only invalidates a *user's own* tokens. Cross-device revocation is global per account (one counter) — acceptable for this app's single-user/admin model.
- No password change/reset feature exists to hook; the primitive is in place for when one is added.

## 9. Deliberately Deferred (out of P3.4 scope)

- Cookie/httpOnly token storage, CSRF hardening, CSP.
- Admin account deactivation/activation endpoints (none exist; the live status check already covers enforcement if status is changed out-of-band).
- Password change/reset feature; token blacklist; OAuth/OIDC; Redis-backed sessions; multi-session-with-selectable-invalidation.
- Anything P4 (deployment) — not started.
