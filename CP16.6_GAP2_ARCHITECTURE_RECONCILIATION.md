# CP16.6 GAP #2 — ARCHITECTURE RECONCILIATION
**Enabled-State Ownership: `JobSource.enabled` vs SKILL.md `enabled`**

**Date:** 2026-09-13
**Scope:** READ-ONLY reconciliation of Gap #2 only (CP16.5 Section 8 / CP16.6 Section 3)
**Status:** NO SOURCE CODE MODIFIED — this document changes nothing. All findings verified against the listed files at commit `ab6beab`.

---

## 0. WHY THIS REPORT EXISTS

CP16.5/CP16.6 identified Gap #2 as: *CP15.5 auto-disables a portal via SKILL.md `enabled: false`, but `JobSource.enabled` in the database is unchanged, so the admin UI and the runtime disagree.* The initial fix proposal (Option A in CP16.6 §3.4 — "CP15.5 → DB sync") assumed SKILL.md `enabled` is the runtime source of truth and that the only missing piece was a one-way write from CP15.5 into `job_sources`.

This reconciliation re-examines that assumption against the actual code. It finds the two states are **not** one authoritative state and **cannot** be collapsed into one without removing the file-based agentic execution model that is the product's design. The correct architecture is **two coupled states with a write-through bridge**, and this document specifies that model precisely.

---

## 1. AUTHORITATIVE STATE DEFINITION

The `enabled` concept currently lives in **three** artifacts. They answer different questions and have different write domains:

| Artifact | State fields | Question it answers | Write domain | Source of truth for |
|----------|-------------|---------------------|--------------|---------------------|
| `job_sources` row (SQLite DB) | `enabled` BOOL · `status` ENUM | *"Should this source be running? (administrative intent)"* | Admin UI only (`PATCH /api/admin/sources/{id}`) | **Admin intent / audit ledger** |
| Per-portal `SKILL.md` frontmatter | `enabled: true\|false` | *"Should the `/job-scraper` pipeline run this portal?"* | CP15.5 CLI (auto + manual), agent/human edit | **Runtime execution gate** |
| `portal_health.json` portal entry | `disabled` · `disabled_at` · `disabled_reason` | *"Was this portal disabled, by what, and when?"* | CP15.5 CLI only | **Disable-event bookkeeping** |

**Answer to the framing question:** `JobSource.enabled` and SKILL.md `enabled` are **distinct administrative vs runtime states, not a single authoritative state.** They are coupled by intent but written by different owners, and — critically — only SKILL.md `enabled` has any runtime effect today.

**Per-domain authority — the honest statement:**
- **For execution:** SKILL.md `enabled` is authoritative. It is the only one of the three that gates whether a portal runs.
- **For administration/audit:** `job_sources.enabled` + `status` is authoritative. It records what the admin decided.
- **For disable-lifecycle display:** `portal_health.json` fields are authoritative about *why/when* (auto 403-threshold vs manual).

**Why they cannot be unified (rejecting Option D).** SKILL.md is an open file in the filesystem. The `/job-scraper` skill is agentic and reads it directly; a fork or operator can also edit it (`.claude/skills/job-scraper/SKILL.md:128, 452`). The DB row is a committed, API-accessible record. Making the DB the single gate would force the agentic pipeline to query the database — a migration of how the whole scraper executes, for an outcome the product already achieves by file convention. That refactor is correctly out of scope. The reconciliation target is therefore **consistency between the two, not sameness.**

**New, previously-uncorrected fact:** no code-level consumer reads SKILL.md `enabled`. The `orchestrator.js` → `run_canonicalization.js` path iterates a **hard-coded** `PORTAL_CLI_COMMANDS` map (`run_canonicalization.js:7-62, 183-194`) with no `enabled` check. The gate is enforced **by agentic instruction** in the `/job-scraper` skill, not by mechanism. Consequences:
- If the pipeline runs via `/job-scraper` (normal), disabled portals are skipped.
- If `node job_scraper/orchestrator.js` is invoked directly, the gate is bypassed entirely for every portal.
This caveat belongs in the runtime-state definition and the documentation requirements (§8).

## 2. MUTATION OWNERSHIP

Every current writer of either state, with the evolution proposed by this reconciliation (▲ = new write added):

| Owner | Trigger | Writes today | Proposed write |
|-------|---------|--------------|----------------|
| **Admin UI → `admin_sources.py`** | Admin toggles enable/disable (`JobSources.tsx` → `PATCH`) | `job_sources.enabled` · `job_sources.status` (blind field setter, `admin_sources.py:185-209`) | ▲ **Write-through to SKILL.md `enabled` + health-store disabled fields** (only when `adapter_name` set and enabled toggled) |
| **CP15.5 `check` (auto-disable)** | 403 block rate > 50% strictly (rolling 7-day) | SKILL.md `enabled: false` + `portal_health.json` `disabled=true/at/reason` (`portal_health.js:441-507`) | ▲ **Best-effort DB write**: matching `job_sources.adapter_name` → `enabled=false`, `status=DISABLED` (only rows currently ENABLED) |
| **CP15.5 `enable`/`disable` CLI** | Operator runs `portal_health.js enable/disable <portal>` | SKILL.md `enabled` + health-store fields (`portal_health.js:567-605`) | ▲ **Best-effort DB write** mirroring the same toggle |
| **Agent / human** | `/job-scraper` skips/re-offers, or direct edit | SKILL.md `enabled` (file edit, confirmation-gated per skill `:452`) | *(none — cannot intercept an open-file edit; divergence tolerated and surfaced)* |
| **`run_canonicalization.js`** | Orchestrator discovery stage | — | — (no write; see §3 caution) |

**Shared invariants for the two new write paths:**
1. **Idempotent.** Re-applying the same value is a no-op (`portal_health.js:359-384` sync is already idempotent; DB update should compare-before-write).
2. **Best-effort, never fatal.** A missing DB, missing `job_sources` row, or missing SKILL.md must not fail an admin PATCH or a `check` run — log and continue.
3. **Edit semantics must be copied from CP15.5.** Frontmatter edits must preserve the existing line's comment suffix byte-for-byte, insert a missing key as the first frontmatter key, and **refuse (fail safe) when no YAML frontmatter exists** (`portal_health.js:180-198, 200-208`). The Python side already mirrors the read half (`portal_health.py:38-40`); the write half must re-use the same rules.
4. **Adapter-name join key.** `portal_health.js` works in skill-name space (`normalizePortalName`, `portal_health.js:124-128`); `job_sources.adapter_name` stores skill names ("indeed-search"). The DB direction joins on `adapter_name == skill name`. `job_sources.name` is the base name ("indeed") and is **not** the join key for this bridge.

## 3. READ / CONSUMER OWNERSHIP

| Consumer | Reads | Policy today | Proposal |
|----------|-------|--------------|----------|
| **`/job-scraper` skill** (agentic) | SKILL.md `enabled` | Skip disabled portals, record in Step 5 summary | Unchanged — keep as the execution gate |
| **`portal_health.js status` CLI** | SKILL.md `enabled` + health store | Read-only | Unchanged |
| **`portal_health.py` health API** (`GET /api/health/portals`) | SKILL.md `enabled` via `_read_skill_enabled` (`portal_health.py:54-82, 98`) | Read-only | ▲ **Also read `job_sources.enabled`** and expose both as separate fields so divergence is visible, never silent |
| **`orchestrator.js` / `run_canonicalization.js`** | **Nothing** (hard-coded `PORTAL_CLI_COMMANDS`) | Runs every listed portal | **No code change recommended** — but see caveat: direct orchestration bypasses the gate. Document it (§8) |
| **Admin UI (`JobSources.tsx`)** | `job_sources` | Shows badge from DB | ▲ Optionally annotate badge when DB ↔ SKILL diverge (read of health API field) |
| **`admin_sources.py` PATCH** | — | Blind setter | ▲ Add adapter-name guard (§5) |

**Design principle:** read consumers keep their current data source; the bridge and the dual-field health API make the two states *visible* and *reconciled at each mutation* rather than forcing every reader onto a single source.

## 4. STATE-TRANSITION TABLE

Legend: `I` = intent (`job_sources.enabled`), `R` = runtime (SKILL.md `enabled`), `D` = health-store `disabled`. Arrows show current behavior; parenthetical shows the post-bridge behavior.

### 4.1 Current behavior (the gap)

| # | Trigger | I (`job_sources.enabled`) | R (SKILL.md) | D (health `disabled`) | Consistency |
|---|---------|---------------------------|--------------|------------------------|-------------|
| T1 | Admin enables | `false → true` | untouched (`false` typically) | untouched | **DIVERGED** — admin sees "Enabled"; runtime still off |
| T2 | Admin disables | `true → false` | untouched (`true`) | untouched | **DIVERGED** — admin sees "Disabled"; runtime still runs |
| T3 | CP15.5 auto-disable (`check`, 403>50%) | untouched (`true`) | `true → false` | `false → true` | **DIVERGED** — runtime off; admin badge stale |
| T4 | CP15.5 manual `enable` | untouched (`false`) | `false → true` | `true → false` | **DIVERGED** — runtime on; admin badge stale |
| T5 | CP15.5 manual `disable` | untouched (`true`) | `true → false` | `false → true` | **DIVERGED** |
| T6 | Agent/human edits SKILL.md | untouched | `→ target` | untouched | **DIVERGED** (unavoidable) |
| T7 | `check` re-run, 403 rate recovered | untouched | stays `false` | stays `true` | *(no auto re-enable — by policy)* |

Every transition except the never-occurring aligned case diverges today. That is Gap #2 in table form.

### 4.2 Post-bridge behavior (this reconciliation)

| # | Trigger | I | R | D | New write(s) | Consistency after bridge |
|---|---------|---|---|---|--------------|--------------------------|
| T1 | Admin enables | `→ true` | `→ true` | `→ false` (clear) | PATCH also writes SKILL.md + clears health fields | **ALIGNED**; admin enable is the operator re-enable (manual, per no-auto-re-enable policy) |
| T2 | Admin disables | `→ false` | `→ false` | `→ true` (reason `admin disable`) | PATCH also writes SKILL.md + sets health fields | **ALIGNED** |
| T3 | CP15.5 auto-disable | `→ false` (if current row ENABLED) | `→ false` | `→ true` | `check` also updates DB (best-effort) | **ALIGNED** |
| T4 | CP15.5 manual `enable` | `→ true` (restore) | `→ true` | `→ false` | `enable` CLI also updates DB (best-effort) | **ALIGNED** |
| T5 | CP15.5 manual `disable` | `→ false` | `→ false` | `→ true` | `disable` CLI also updates DB (best-effort) | **ALIGNED** |
| T6 | Agent/human edits SKILL.md | untouched | `→ target` | untouched | — (cannot intercept) | **VISIBLE DIVERGENCE** — surfaced via dual-field health API, not silent |
| T7 | `check` re-run, rate recovered | unchanged | stays `false` | stays `true` | — | Aligned (both off). No auto re-enable |

**Precedence and race note:** when admin and CP15.5 race (e.g., admin enables while `check` auto-disables), the loser's write wins atomically per artifact; because each bridge writes **both** fields per transition, no partial/ghost state is produced — the last completed transition defines the consistent pair. Both write paths are idempotent, so a final reconciliation `check` converges one-way.

**Guard on T3:** auto-disable must only flip `job_sources` rows currently `ENABLED` (or `enabled=true`). It must silently skip rows in `APPROVED`/`READY_FOR_REVIEW`/`DISCOVERED` — those were never running, so there is no intent to override, and flipping them to `DISABLED` would corrupt the lifecycle state machine.

## 5. SMALLEST IMPLEMENTATION SCOPE

Ordered by size; the first two close the gap. The third is cheap diagnostic visibility. The fourth is a one-line safety valve. Everything else stays out of scope.

### 5.1 Admin PATCH write-through (backend, ~30 lines + tests)
In `backend/app/routers/admin_sources.py`, inside the existing `PATCH /{source_id}` handler (`admin_sources.py:185-209`): when `enabled` is present in `update_data`, after the DB commit, perform a **write-through**:
- Resolve skill dir from `source.adapter_name`. If `adapter_name` is null/unknown → **skip** and (new validation, §5.4) reject the enable.
- Write `.agents/skills/{adapter_name}/SKILL.md` `enabled` with CP15.5-identical edit semantics (new small Python helper mirroring `setEnabledInContent`; place next to the existing read helpers in `portal_health.py` or a shared module).
- Update the matching `portal_health.json` entry: on enable clear `disabled/disabled_at/disabled_reason`; on disable set `disabled=true`, `disabled_at=now`, `disabled_reason="admin disable"`.
- Atomic + read-back verify per CP15.5 convention; any failure → 500 with no half-state (or 409 with detail), and DB change rolled back if the file write fails.

### 5.2 CP15.5 → DB write-through (node, ~25 lines + tests)
In `job_scraper/portal_health.js`:
- Add `dbFile` default `path.join(__dirname, '..', 'backend', 'careerpilot.db')` (+ env `PORTAL_DB_FILE`).
- Add a small **best-effort** helper `syncJobSourceDisabled(skillName, enabled)`:
  - Parameterized SQLite UPDATE on `job_sources SET enabled=?, status=? WHERE adapter_name=?` with `status` per Strategy B TEXT values (`'enabled'`/`'disabled'`).
  - Guard: for disable, only update rows whose current `status='enabled'` (skip APPROVED/READY/DISCOVERED rows — §4.2 guard).
  - Wrap in try/catch; **never throw** — on failure log and continue (check must not fail because the DB is absent, which is the normal case when no source row exists).
- Call it from `planCheckSummary`/`runCheck` after each auto-disable (`portal_health.js:441-507`) and from `manualToggle` (`portal_health.js:575-605`), before/after persisting health.

### 5.3 Health API divergen ce visibility (backend, additive)
In `portal_health.py` `_build_portal_status`/`list_portal_health`: read `job_sources.enabled` for the portal (by `adapter_name`), add `job_source_enabled: Optional[bool]` alongside `skill_enabled` in the response schema. Zero cost to existing readers; the UI/operator can see drift (T6) instead of guessing.

### 5.4 Enable guard (backend, validation)
In `PATCH`: reject `enabled=true` when `adapter_name` is null or not a known `PORTAL_BASE_TO_SKILL` value (422/400). A source cannot be running with no runtime adapter. Back-fill note: if any existing row is `enabled=true` with a null adapter, block enable-flip until adapter set (safe today — table starts empty per the corrective migration).

### Explicitly OUT of scope (rejected, per CP16.6 §7)
- Option D unification (DB as sole gate / SKILL.md removal).
- Making `orchestrator.js` read `enabled` (would move the gate into code and change `/job-scraper` semantics; a separate RFC).
- Event bus / real-time sync.
- `candidate_profiles` auto-init, admin-users tests — those are Gap #1 / Gap #3; not this report.

## 9. REVISED CP16.7 VERIFICATION CRITERIA

A CP16.7 pass (READ-ONLY) must confirm **all** of:

1. **Admin → runtime write-through.** Admin enables a source with `adapter_name` set → within the same action, `.agents/skills/{adapter_name}/SKILL.md` reads `enabled: true` **and** `GET /api/health/portals` reports `skill_enabled=true` for it.
2. **Admin → runtime disable.** Admin disables → SKILL.md `enabled: false` and health entry `disabled=true`, `disabled_reason="admin disable"`.
3. **CP15.5 → DB write-through.** Forced auto-disable (fixture with >50% 403 rate): within one `check` run, a matching `job_sources` row (currently `ENABLED`) flips to `enabled=false / status=disabled`. A portal with **no** `job_sources` row does not fail the run.
4. **Manual re-enable restores intent.** `portal_health.js enable <portal>` after an auto-disable → `job_sources.enabled=true` restored.
5. **Lifecycle guard.** Auto-disable never flips a row in `APPROVED`/`READY_FOR_REVIEW`/`DISCOVERED`.
6. **Divergence is visible, not silent.** With a simulated agent edit of one SKILL.md (T6), `/api/health/portals` shows `skill_enabled` disagreeing with `job_source_enabled`.
7. **Enable guard.** `PATCH enabled=true` with missing/unknown `adapter_name` → 422, SKILL.md untouched.
8. **Idempotency.** Re-applying the same toggle produces no byte churn or DB write; `check --dry-run` writes nothing.
9. **Full regression.** All 336 backend tests, all existing `portal_health.test.js` cases, and the new §6 tests pass.
10. **Documented caveat.** The direct-`orchestrator.js`-bypasses-gate caveat is recorded in `.claude/skills/job-scraper/SKILL.md`.

**If any of 1–8 fails, the bridge is not closed and CP16.7 reports a partial result with the failing transition named — no code changes are made during verification itself.**
