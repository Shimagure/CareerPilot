## Resolved Policy (as mandated)

1. **Auto-disable: YES.** When a portal's 7-day explicit-403 rate exceeds the threshold, CP15.5 automatically applies `enabled: false` with no confirmation gate.
2. **A 403 IS valid blocked evidence; it is NOT parser breakage.** `http_403` is the evidence that counts. Parser breakage is a separate concept and is never interpreted as a 403. 429s and generic block-page detections are **inconclusive** and never count as 403s.
3. **Threshold window:** a 7-day rolling window. Rule — *more than 50% of observed portal results in the window are explicit 403-blocked results → disable.* The denominator is actual observed results. No invented formula, weighted score, or alternate percentage.
4. **Health API** is CP15.6 territory. CP15.5 owns collection, history, status calculation, and the SKILL.md toggle only.
5. **Re-enable is strictly manual:** `node job_scraper/portal_health.js enable <portal>` touches only that portal's SKILL.md, sets `enabled: true`, preserves unrelated frontmatter/body, never alters health history, and never touches other portals.

## Health Data Schema — `portal_health.json`

```json
{
  "schema_version": "1.0",
  "rolling_window_days": 7,
  "disable_threshold_percent": 50,
  "updated_at": null,
  "portals": {
    "indeed-search": {
      "name": "indeed-search",
      "observations": [
        { "evidence_id": "<stable_id|run_id>", "observed_at": "ISO", "result": "success|explicit_403_blocked|inconclusive", "source": "seen_jobs" }
      ],
      "counts": { "success": 0, "explicit_403_blocked": 0, "inconclusive": 0, "total_observed": 0 },
      "status": "ok|blocked|insufficient_evidence",
      "window": { "explicit_403_blocked": 0, "success": 0, "inconclusive": 0, "total_observed": 0, "block_rate_percent": null },
      "disabled": false,
      "disabled_at": null,
      "disabled_reason": null
    }
  }
}
```

- **No fake historical observations.** The shipped `portal_health.json` has empty `observations` for all 10 portals; observations are added only from real evidence during `check`.
- **Deterministic schema.** `validateHealth` rejects missing/invalid version, window days, threshold, or malformed portal entries (including `portals` being an array).
- **Atomic writes.** Every persist goes through temp-file + rename. No `.tmp` leftovers.
- **Idempotent updates.** `syncObservations` aligns stored observations to current evidence by `evidence_id` (`stable_id`; `run:<id>` for run-level sources): stale evidence dropped, new evidence appended, duplicates impossible. Re-running `check` with identical evidence is a no-op.

## Evidence Classification (ingestion)

Evidence is reused from the pipeline artifact that actually carries per-portal access evidence: **`seen_jobs.json`** (the same source CP15.4's `derivePortalHealth` uses). CP15.4 `run_history.json` currently carries **no per-portal evidence** (it's empty, and stage records have no portal breakdown), so it is not yet an evidence source — the run-level portal evidence shown in CP15.4's summary originates from `seen_jobs.json` too. When a future run populates `run_history` with portal evidence, a run-level evidence source can fold in via the same classifier.

Per job record:

| Record state | Classification | Effect |
|---|---|---|
| `blocked_reason` == explicit 403 marker (`http_403`, `403`, `forbidden`) | `explicit_403_blocked` | Counts toward numerator **and** denominator |
| `blocked_reason` == 429 / rate-limit / generic block page / captcha | `inconclusive` | Denominator only; **never** a 403 |
| no `blocked_reason`, usable timestamp | `success` | Denominator only (portal returned a usable result) |
| no usable timestamp, or no portal attribution | skipped | Unattributable evidence is never counted |
| no evidence for the portal in the window | `missing` (derived) | **Never an observation, never in the denominator; missing data does not disable** |

Observation timestamp priority: `blocked_at` → `last_verified` → `changed_at` → `first_seen`.

**Portal name normalization:** `seen_jobs` stores base names (`indeed`); SKILL dirs are `indeed-search`. Evidence is normalized to the `-search` name.

## 7-Day Rolling Window & the Exact >50% Rule

`computeWindowStatus(observations, now, windowDays=7, thresholdPercent=50)`:

```
cutoff = now - 7 days
in-window = observations with observed_at in [cutoff, now]
total_observed = success + explicit_403_blocked + inconclusive   (in window)
block_rate = explicit_403_blocked / total_observed
status = total_observed == 0  → "insufficient_evidence"
         block_rate * 100  >  50 → "blocked"
         otherwise               → "ok"
```

- **Disable trigger is strictly greater than 50%.** Exactly 50% does **not** disable.
- **Insufficient/no evidence does not disable.** An empty window (or no observations) yields `insufficient_evidence`; missing data is not failure.
- 429s and generic block pages may push the denominator up but never the numerator.

## Automatic Disable Behavior

When a portal's window status is `blocked` and it is not already disabled, `check`:

1. Sets that portal's SKILL.md frontmatter to `enabled: false`, preserving the existing comment suffix byte-for-byte (e.g. `enabled: false  # set to false to keep this portal installed but have /scrape skip it`).
2. Writes **only** that portal's file — other portals are never opened for writing and remain byte-identical.
3. Updates the health store: `disabled: true`, `disabled_at` (ISO), `disabled_reason: "threshold-based 403 access blocking"`.
4. Emits a structured log: `[INFO] portal disabled by 403 threshold (portal=indeed-search, reason=threshold-based 403 access blocking)`.

**Transactional SKILL.md writes:** all files targeted by one `check` are transformed in memory first — any unsafe structure aborts **before** a single write — then applied atomically with read-back verification. A failure exits non-zero without leaving a half-updated file.

**No automatic re-enable.** A portal's `enabled` flag is only ever returned to `true` by the manual CLI.

## Manual Re-enable / Disable

```
node job_scraper/portal_health.js enable <portal>    # SKILL.md enabled:true
node job_scraper/portal_health.js disable <portal>   # SKILL.md enabled:false
```

- Modifies **only** the target portal's SKILL.md `enabled` key (comment suffix + body preserved).
- Updates the target's health-store `disabled` fields (`disable` records reason `manual disable` + `disabled_at`; `enable` clears them).
- **Never touches health history** (`observations` are left exactly as they were).
- With no enabled key present, the op inserts `enabled: <value>` as the first frontmatter key using the project comment convention (required so a portal with no key can be toggled). A SKILL.md with no YAML frontmatter at all is refused (unsafe structure → non-zero exit).

---

## SKILL.md Safety Guarantees

- Edits are restricted to the YAML **frontmatter**, and within it only the `enabled:` line.
- The existing line's boolean is swapped in place; the comment suffix is preserved identically (both `enabled: true` and `enabled: false` variants verified by tests).
- The post-frontmatter body is untouched — byte-for-byte.
- Atomic write (temp + rename) + read-back verification of the resulting `enabled` value.
- Only the affected portal's file is ever written; untouched portals are byte-identical (tests assert this).
- Portals whose name fails `^[a-z0-9]+(-[a-z0-9]+)*$` (path traversal, punctuation) are rejected.

## CLI

```
node job_scraper/portal_health.js <command> [options]

Commands:
  check          Ingest evidence, evaluate the rolling 7-day window, auto-disable
                 any portal whose explicit-403 rate is > 50%. Persists portal_health.json.
  status         Read-only: per-portal health window + current SKILL.md enabled state.
  disable <p>    Manual disable (SKILL.md enabled:false).
  enable <p>     Manual enable (SKILL.md enabled:true). No automatic re-enable.
  --help, -h     Usage, exit 0.

Options:
  --health-file <path>    portal_health.json path
  --seen-jobs <path>      seen_jobs.json evidence path
  --skills-dir <path>     .agents/skills directory (or env PORTAL_SKILL_DIR)
  --now <ISO>             evaluation clock override (tests)
  --dry-run               check computes + prints; writes nothing, edits nothing
```

Safe failure (non-zero, no writes): malformed health data, missing health file for `status`, missing `seen_jobs`/malformed JSON for `check`, invalid portal names, missing portal skill, unsafe SKILL.md structures, unknown commands/options.

## Limitations

- **Evidence attribution is timestamp-based.** Records without a parseable timestamp are skipped (conservative: unattributable evidence is never counted).
- **`run_history.json` is not yet an evidence source** because it carries no per-portal evidence today; the classifier is ready to fold it in once it does.
- **`seen_jobs` success evidence is inclusive** — every non-blocked record with a recent timestamp counts as one observed "success" result. This is deliberate: it makes the denominator real observed portal results. 403s must genuinely dominate to trigger a disable.
- **No ring/decay model.** Settings changes (`rolling_window_days`, `disable_threshold_percent`) apply at the next `check`; historical observations are not re-stamped.
- **Auto-disable is one-way by policy**; recovery is manual by design (no automatic re-enable).
