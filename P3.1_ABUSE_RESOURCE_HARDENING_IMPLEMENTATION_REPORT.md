# P3.1 — Abuse Controls and Resource-Exhaustion Hardening: Implementation Report

- **Scope:** P3.1 only (abuse controls + resource-exhaustion hardening). P3.2 areas are explicitly **out of scope** and were not touched.
- **Baseline HEAD:** `85a5c32e93818fe25b6f3bbf4e1ec8506b67f517` (P2 production configuration)
- **Status:** Implemented and fully validated. Single commit created; no push performed.
- **Date:** 2026-09-14

---

## 1. Implementation Summary

The two HIGH public-launch blockers addressed are **unbounded account-level abuse** (open self-service registration, no rate limiting on login/registration) and **unbounded expensive workload initiation** (`/api/search` background scraping and `/api/applications/with-documents` LaTeX generation), plus the **globally monopolizable search lock**.

All protection is **in-process and dependency-free** — appropriate for the current single-host, single-worker SQLite deployment. No Redis or external service was introduced. State is strictly bounded (LRU-capped key store). No permanent account locking and no CAPTCHA / third-party services were added. P1 (public/private boundary) and P2 (production configuration) behavior is preserved unchanged and re-verified.

A **pre-existing bug** was discovered and minimally fixed on the way: `POST /api/applications/with-documents` referenced `_build_profile_response`, which does not exist anywhere in the codebase (verified against `git show ab6beab:backend/app/routers/profile.py`), causing every request to that endpoint to fail with an internal 500 regardless of input. The call was corrected to the real `_profile_to_response(profile_model, None)`. Without this fix, the P3.1 document-generation protections would have guarded a workflow that could never succeed. This is reported here because it is a behavior change beyond pure hardening (see §8).

## 3. Exact Rate / Concurrency Policies

All scopes default to enabled; `RATE_LIMIT_ENABLED=false` disables enforcement (dev/test escape hatch).

| Scope | Identity | Policy | Default limits |
|-------|----------|--------|----------------|
| `auth.login` | Client IP | slider window | 20 per 300 s |
| `auth.login.account` | Lowercased account email | sliding window | 10 per 900 s |
| `auth.register` | Client IP | sliding window | 10 per 3600 s |
| `search.start` | User id (JWT `sub`) | sliding window | 6 per 300 s |
| `docgen.generate` | User id (JWT `sub`) | sliding window | 10 per 3600 s |
| doc-gen concurrency | User id | per-key in-flight guard | max 1 concurrent, retry-after 10 s |
| search run lifecycle | — | global single-run lock + watchdog | max 1200 s per run |

On any exceeded sliding-window limit the server returns **HTTP 429** with a generic body (`Too many requests. Please try again later.` — a concurrency-blocked doc-gen returns its own safe message) and a `Retry-After` header. No 429 body or header reveals stack traces, filesystem paths, SQL details, the lock implementation, environment values, or the configured limit.

## 4. Rationale per Protected Endpoint

### 4.1 Login (`auth.login.ip`)
- **Why:** login is unauthenticated and reaches password verification work; a burst of guessed credentials is the cheapest way to hammer the app.
- **Shape:** 20 per 300 s per IP — generous for real users behind a NAT, small enough to stop brute-force scripts. A second, **per-account** limit (`auth.login.account`, 10 per 900 s) applies regardless of IP, so rotating IPs cannot brute-force one account. No permanent lockout — the window simply slides out.
- **Identity:** per-IP uses the peer address (`X-Forwarded-For` only when `RATE_LIMIT_TRUST_PROXY=true`); per-account uses the lowercased email from the request body, which is additionally useful as a cheap enumeration deterrant.

### 4.2 Registration (`auth.register`)
- **Why:** self-service registration is the open-hole an attacker uses to mint accounts; each account is a resource in the DB.
- **Shape:** 10 per 3600 s per IP. Legitimate signup is rare; this allows normal use while throttling account-farming.
- **Identity:** peer IP (default), or `X-Forwarded-For` first entry when trust-proxy is explicitly enabled.

### 4.3 Search initiation (`search.start`)
- **Why:** `POST /api/search` launches an expensive multi-portal scraping pipeline in the background. Without a limit a single user could queue an unbounded number of runs.
- **Shape:** 6 per 300 s **per user**, keyed by the authenticated user id (JWT `sub`) — never by client-controlled input. The limit is enforced **inside the handler after request-body validation**, so malformed requests (422) never consume a slot; only requests that will actually reach the pipeline are counted. Existing tests that make up to 5 sequential valid runs still pass.
- **Interaction with the global lock:** the rate limit bounds how many runs a user can attempt over time; the global single-run lock bounds how many can ever be queued concurrently. Both combine: the first request either acquires the lock or gets 409; further attempts within the window get 429.

### 4.4 Document generation (`docgen.generate` + concurrency guard)
- **Why:** `POST /api/applications/with-documents` compiles LaTeX (pdflatex/lualatex, xelatex) synchronously per request — CPU- and disk-heavy. Uncontrolled simultaneous generations by one user would exhaust CPU.
- **Shape:** 10 per 3600 s per user (sliding) **plus** a per-user concurrency guard of **max 1 in-flight** generation. A second concurrent generation is refused with 429 and `Retry-After: 10`. The guard is released in a `finally` on every exit path, so a failing compile cannot retain the slot (no permanent monopolization).
- **Doc-gen stays authenticated-only** (the endpoint already required `get_current_user`; the limits are layered on top). CP13 factual-safety and LaTeX escaping are untouched.

### 4.5 Not rate-limited (deliberately)
Read-only listing/get endpoints, application CRUD, resume/profile reads, admin, dashboard, public demo, and job-data endpoints are **not** rate-limited: they are cheap, authenticated, and DB-local. Throttling them would add noise without materially reducing risk.

## 5. Search-Lock / Resource-Exhaustion Behavior

The single-search global lock (DB-backed, reject-if-any-QUEUED/RUNNING → 409) is **preserved as the intended design**; no second, conflicting locking system was added. Resource hardening on top:

1. **Per-user start limit** (§4.3) bounds run *attempts*.
2. **Max-run-duration watchdog (`search_run_max_duration_seconds=1200`):** the background execution is wrapped in `asyncio.wait_for`. A pipeline that exceeds 20 minutes is signalled, finalized as `FAILED` (pipeline error `Execution timed out.`), and the global lock is thereby freed so the run cannot monopolize search forever.
3. **Phase-1 finalization fix:** if the background task fails to transition the run QUEUED → RUNNING (e.g. the queue was interrupted before processing), the run is now finalized as `FAILED` (metadata `pipeline_stage=failed`) instead of being abandoned in the `QUEUED` state. Previously a leftover QUEUED row could block the global lock indefinitely — every subsequent start attempt would 409.
4. **Startup reconciliation already existed** in `main.py` (stale runs reconciled on boot) and was not touched.

Net effect: one user can start at most 6 runs / 5 min; only one run ever executes at a time; no run can stay in-flight longer than 20 minutes; no run can remain stuck QUEUED.

## 6. Document-Generation Protection

- Endpoint remains **authenticated-only** (unchanged pre-P3.1).
- **Rate limit** `docgen.generate`: 10 per 3600 s per user (user-id keyed).
- **Concurrency guard** `DOCGEN_GUARD`: max 1 in-flight generation per user; a second simultaneous request within that window → 429 with `Retry-After: 10`; slot released via `finally`.
- **No persistent quotas:** memory/CPU protection is achieved with in-process windows and the guard — nothing is written to the DB, so nothing needs periodic cleanup and legitimate usage is never permanently capped.
- The `cv_error`/`cover_letter_error` strings are only surfaced on a generation failure (HTTP 500) in a **single-line detail**; they are pipeline-produced messages, not internal dumps, and do not change P3.1 error-safety requirements.

## 9. Known Limitations and Future Scaling

- **In-process/per-process limits:** each uvicorn worker keeps its own windows. Correct today (the app runs a single worker on SQLite); if the app later runs multiple workers, limits are per-worker — acceptable for launch, but to enforce globally, move the limiter to a shared store (Redis) or a single worker with thread/async sharding.
- **`X-Forwarded-For` trust is opt-in and assumes a single trusted reverse proxy** that overwrites the header; without it, clients cannot forge the header because they cannot reach the app directly. If the proxy topology changes, revisit.
- **Memory bound is per-process** (`RATE_LIMIT_MAX_CLIENTS=10000` keys, ≤ `limit` events each via LRU eviction + sweeps). No unbounded in-memory growth.
- **No persistent quotas** for doc-gen today; if sustained abuse of the 10/3600 window ever becomes a concern, a per-user token bucket or DB-backed quota is the natural next step.
- Search **timeout is coarse** (per-run 1200 s); per-portal timeouts already exist inside the pipeline adapter. A finer-grained per-portal budget is a possible future refinement, not required at launch.
