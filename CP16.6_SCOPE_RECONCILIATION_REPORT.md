### 2.1 Current Registration Flow (`backend/app/routers/auth.py:96-130`)

```python
@router.post("/register", response_model=Token, status_code=status.HTTP_201_CREATED)

    # Check if email already exists

    existing_user = result.scalar_one_or_none()
    if existing_user:
        raise HTTPException(status_code=400, detail="Email already registered")

    # Create new user

        name=user_data.name,
        email=user_data.email,
        password_hash=hashed_password,
        status=UserStatus.ACTIVE,
    )
    session.add(user)
    await session.commit()
    await session.refresh(user)

    # Create access token with role claim
```

### 3.2 Divergence Scenarios

| Scenario | JobSource.enabled | SKILL.md enabled | Health API (skill_enabled) | User Impact |
|----------|-------------------|------------------|---------------------------|-------------|
| Admin enables in UI | `true` | `false` (default) | `false` | Orchestrator skips source; admin sees "Enabled" |
| CP15.5 auto-disables | `true` (stale) | `false` | `false` | Admin UI shows green "Enabled"; orchestrator skips |
| Admin disables in UI | `false` | `true` (stale) | `true` | Orchestrator runs; admin sees "Disabled" |
| Both aligned | `true` | `true` | `true` | ✅ Consistent |
| Both aligned | `false` | `false` | `false` | ✅ Consistent |

### 3.3 Architecture Options Analysis

| Option | Description | Pros | Cons | Effort |
|--------|-------------|------|------|--------|
| **A: CP15.5 → DB Sync** | CP15.5 `check` command also writes `JobSource.enabled = false` via internal API or direct DB write | Single source of truth (SKILL.md); minimal CP16 changes; CP15.5 already has portal name | CP15.5 needs DB access; couples CP15.5 to CP16 schema; requires internal admin endpoint | Medium |
| **B: CP16 Polling Sync** | CP16 adds background job (scheduler) to periodically read SKILL.md and sync to `JobSource.enabled` | CP16 owns its model; decoupled; admin UI always eventually consistent | Polling interval latency; eventual consistency only; adds scheduler dependency | Medium |
| **C: Health API Reads JobSource** | Modify `/api/health/portals` to read `JobSource.enabled` instead of (or in addition to) SKILL.md | Health API reflects admin UI truth; simple change | Breaks CP15.5 autonomy; CP15.5 auto-disable no longer reflects in health API without DB sync | Low |
| **D: Unified Source (Recommended)** | **Make `JobSource.enabled` the single source of truth.** CP15.5 auto-disable writes to DB via new internal endpoint. SKILL.md `enabled` becomes derived/read-only or removed. | Single truth; clean separation; CP15.5 triggers → DB → UI/API all consistent | Requires CP15.5 to call internal API; schema migration if SKILL.md `enabled` removed; biggest refactor | High |

### 3.4 Recommendation: Option A (CP15.5 → DB Sync) — Pragmatic Balance

**Rationale:**
- CP15.5 already owns the disable decision logic (rolling window, 403 threshold)
- CP15.5 already iterates all portals in `planCheckSummary()` → natural place to add DB write
- Requires only an internal endpoint in CP16 (e.g., `POST /api/admin/sources/sync-enabled`) or direct SQLAlchemy write
- Preserves CP15.5 autonomy while fixing the divergence
- Lower risk than Option D (no schema migration, no SKILL.md removal)

**Implementation Sketch (Option A):**
```python
# In CP16: backend/app/routers/admin_sources.py (new internal endpoint)
@router.post("/sync-enabled", dependencies=[Depends(get_internal_service_user)])  # or API key
async def sync_enabled_states(
    updates: List[Dict[str, Any]],  # [{"portal": "indeed-search", "enabled": false}, ...]
    session: AsyncSession = Depends(get_db_session)
):
    for u in updates:
        result = await session.execute(
            select(JobSource).where(JobSource.adapter_name == u["portal"])
        )
        source = result.scalar_one_or_none()
        if source:
            source.enabled = u["enabled"]
            if not u["enabled"]:
                source.status = JobSourceStatus.DISABLED
    await session.commit()
    return {"synced": len(updates)}
```
